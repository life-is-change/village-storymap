# 4060 平台性能优化与验证（2026-10-08）

本轮已将修改放回原本地项目的 main 工作目录。没有提交或推送 Git，没有发布 GitHub Pages，也没有更新 4090 的 Docker、数据库或阿里云。原首页入口、权限和界面布局保持原有方式。

## 真实浏览器对照结果

设备为 RTX 4060 Laptop GPU，使用本机浏览器、同一已登录管理员账号、本地 localhost:9010 和实际 Supabase 数据。基线为 main 提交 `34d2dff161f67455133fb3ae32f545ce5ddeb747`。以下操作优化前、优化后各测三轮；中位数用于减少单次网络波动的影响。

| 操作与测量边界 | 优化前三轮（秒） | 优化后三轮（秒） | 中位数前 → 后 |
| --- | --- | --- | --- |
| 已加载道路图层关闭后恢复：refresh2DOverlay 完成 | 1.103 / 0.713 / 0.648 | 0.002 / 0.002 / 0.002 | 0.713 → 0.002 秒 |
| 已初始化的三维重复进入：3d_enter 完成 | 1.874 / 4.462 / 2.386 | 0.652 / 1.405 / 0.944 | 2.386 → 0.944 秒 |
| 打开已有场景方案：openSceneStudioWorkspace 完成 | 5.832 / 9.653 / 11.605 | 4.836 / 2.522 / 3.792 | 9.653 → 3.792 秒 |

**图层的 2 毫秒是程序更新矢量数据的耗时，不是从点击到屏幕全部绘制完成的耗时。** 图层开关仍可能触发旁边的信息、照片等后台读取。改善的原因是复用已渲染的数据，避免为恢复同一图层重新查询数据库。

三维和场景设计包含真实网络请求，两组测试的网络状态并非严格相同。因此这些是本轮观测到的改善，不能承诺以后每次都有相同比例的提升。场景测试使用已有“管理员试用方案”的 6 个对象，仅打开和退出，没有修改或上传方案。

米埗村显示完整图层时两组均为 211 个矢量要素（建筑 194、道路 14、水体 2、填充 1），道路关闭后均为 197；数据摘要一致，未通过少加载矢量来缩短计时。

### 村庄切换与首次进入

优化后切到红星村一次为 **5.688 秒**，返回米埗村一次为 **3.837 秒**；其中矢量更新分别占 3.487、2.870 秒。优化前切到红星村一次为 29.597 秒，返回米埗村一次等待 117.572 秒后报 SUPABASE_ERROR。只有一次有效前后切换样本，且存在网络失败，不能据此给出稳定的提升百分比。

优化后首次进入平台的一次有效测量为 4.351 秒，其中矢量更新约 3.591 秒。优化前、后都观察到远程账号/数据请求的长尾等待或失败（约 74–94 秒的账号读取、超时的村庄读取等），没有把这些异常样本混入三轮操作的中位数。**本轮没有消除外部网络和 Supabase 请求超时。**

首次冷启动三维的一次计时未完整覆盖 enter，模块文件加载时间不能代表整个三维就绪时间，因此不公布首次冷启动的改善比例。

## 实际改动及对应卡点

| 卡点 | 本轮处理 | 限制 |
| --- | --- | --- |
| 首页入口卡住 | 保留已解决的入口逻辑，实际登录状态下进入并完成后续操作 | 本轮没有重新注册或退出账号；这些流程由自动化用例覆盖 |
| 底图与矢量首屏加载 | 数据集文本缓存、请求去重；消除部分多余空间创建请求；旧村庄迟到结果不再覆盖新村庄 | 天地图瓦片仍由外部服务下载；第一次需要的远程数据仍需等待 |
| 图层开关延迟 | 复用已经加载过的图层快照；仅可见性变化不重新读取该图层；不再因图层开关移动相机 | 编辑/强制刷新仍读取最新数据，不能永远使用旧缓存 |
| 三维停在地球界面 | Viewer 创建后立即定位当前村庄范围；建筑可用时先定位；影像、地形和模型恢复不再全部挡住相机定位 | 远程地形、影像、模型失败仍影响完整画面 |
| 三维与右上角实景窗口负担 | 隐藏或返回二维时暂停相应渲染；实景窗口默认使用较轻的分辨率和精细度配置 | 较轻模式可能稍不清晰；保留 sharp 配置。没有进行帧率对照 |
| 多栋贴图模型加载 | 独立对象按最多 3 组并发恢复；同一对象的修改保持顺序；切村/切空间后停止旧队列 | 尚未制作真正的多级 GLB/纹理资源；不能据此承诺 100 栋精细模型流畅 |
| 场景设计进入等待 | 正确确定项目后，初始场景、素材和版本读取并行执行 | 多组并发访问仍受后端容量、资源体积及网络影响 |
| 村庄切换等待 | 减少不必要请求，缓存与过期响应隔离；切换不再排队等旧村庄矢量完成 | 切换仍需要读取村庄、空间和最新编辑数据 |

本轮还修复了审查中复现的异步影像竞争：旧村庄影像晚返回时，不能再替换新村庄影像。身份、村庄和空间变化后，旧请求/模型队列的结果均需检查归属。

数据缓存有 16 个条目、32 MiB、5 分钟的边界，并按账号和数据集身份隔离；账号/村庄变化会清理相应作用域。只归一化 Supabase 文件签名中轮换的 token，实际文件 URL 或版本改变仍是新数据。编辑和强制重建会失效图层快照，失败不会造成自动无限重试。

反复切换二维/三维会保留已存在的三维视角，因此退出场景编辑后，可能仍看着之前操作的区域。最终核对中白模与道路确实已加载，点击“重置视角”后可完整看到建筑范围；这与卡在地球、模型未加载是不同的情况。

4090 中间文件、照片和最终模型的存储位置在本轮没有改变，也没有重新审计服务器磁盘。本轮性能结果不能用来推断数据库已经迁移，或数据会自动存入阿里云。

## 受控调度实验

另用优化前后实际函数做了三轮受控实验，给每个异步任务固定模拟等待：

- 100 个模型任务：优化前 1568 / 1576 / 1560 毫秒；优化后 528 / 532 / 532 毫秒。
- 场景资源读取：优化前 103 / 93 / 91 毫秒；优化后 52 / 47 / 47 毫秒。

它证明有界并发与并行读取减少了串行等待，**不代表真实 100 栋模型的 GPU 解码、贴图显存占用或帧率**。真实大模型仍需要资源体积统计、纹理压缩和生成适当的多级模型/3D Tiles。

## 在你的电脑上体验

修改已经在原项目，按原来方式用 VS Code 启动。首次按 **Ctrl + Shift + R** 强制刷新，避免仍用浏览器缓存的旧脚本。本轮测试页 http://127.0.0.1:9010/ 仍可体验，临时实验计时面板不是产品功能。

目前只改变本地工作目录，GitHub Pages 和 4090 的旧镜像不会自动同步。建议先用这份代码验证你的日常操作，再进行单独的提交与部署。

仍有数秒的首次读取和明显的远程请求长尾。是否值得迁移数据层，应进一步比较同一查询的请求等待、服务器执行时间、资源下载量和浏览器解析耗时；本轮结果不支持“迁移 PostgreSQL 后全部卡顿自然消失”的结论。
