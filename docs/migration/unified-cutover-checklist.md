# Aliyun-only handoff and activation

This is an operator handoff. No commands in this document have been run on the real Aliyun server, Supabase or campus4090 by the local development session. A copied database, passing synthetic tests and a built image are separate from a live migration.

1. Use the final image whose manifest contains successful native and Platform CI runs for that exact Git commit. `build-unified-release.py` verifies those public workflow results before embedding their IDs and matching code/schema hashes. Intermediate images are refused by deployment preflight. The source website configuration remains `source`.
2. On the Windows computer that can reach Supabase PostgreSQL, run `prepare-unified-cutover.py --package-handoff --archive <final-image> --source-output <new-private-directory>`. The existing PostgreSQL17 tools are used, with hidden database password input. This creates a **new** consistent database archive first, then one upload bundle containing the image, five snapshot files and only the private bridge token. NTFS ACL protection is applied before secrets/backups are written. Source SQL/provider deployment credentials stay in `source-private`; they are not put in the image or upload bundle. The tool does not execute source DDL or provider requests.
3. Upload that one `village-handoff-<release>.tar.gz` file outside the website directory. On Aliyun run `deploy-unified-business.py --deploy --handoff <uploaded-file>` from the updated repository. It extracts only eight exact regular-file names, checks lengths/hashes and refuses links/path traversal/unknown entries. It loads and validates the image and performs the unified internal TEST pass. On an interrupted deployment use the same bundle with `--resume`; retain every partial/error artifact. If extraction itself was interrupted before its success receipt, inspect the private input directory instead of deleting or overwriting it automatically.
4. Apply the generated `source-private/source-install.sql` to **the original Supabase project**, in its SQL editor or from the Windows database client. This is the explicit source extension operation: it creates private queue origin boundaries and a dedicated two-connection transport login; it does not point GitHub Pages to Aliyun, freeze its ordinary tables or change shared Auth. Original patched function definitions/ACLs are captured privately before replacement. Keep the SQL file/password out of chat and Git.
5. With the Supabase CLI authenticated to the correct account, deploy only the two new transports from the reviewed repository:

   ```text
   supabase secrets set --project-ref rzmbmwauomzwiyenafha --env-file <source-private/source.env>
   supabase functions deploy aliyun-task-bridge --project-ref rzmbmwauomzwiyenafha --use-api
   supabase functions deploy aliyun-facade-cloud --project-ref rzmbmwauomzwiyenafha --use-api
   ```

   The source key/provider environment remains server-side. Both new entries alone use their custom private-token authentication; existing browser-facing function settings are preserved. These CLI options follow the [official secrets guide](https://supabase.com/docs/guides/functions/secrets) and [CLI deployment reference](https://github.com/supabase/cli/blob/develop/apps/cli/docs/go-cli-reference.md). Never upload `source.env` or `source-install.sql` to the public web directory. A transport TLS/role/Edge error must be fixed before activation; it is not solved by changing a Publishable key.
6. Update the4090 Worker checkout to the same reviewed commit, retaining its existing environment/service configuration, and restart the relevant existing Worker services. New processes emit `geo-aliyun-bridge-v1` / `facade-aliyun-bridge-v1`. An old process that remains active prevents new private jobs of that kind from entering the queue. The Aliyun server never directly controls a campus GPU. Map worker village IDs only by exact UUID identity or a private explicit JSON mapping whose target is checked against the live source status. An unresolved legacy alias yields `WORKER_VILLAGE_MAPPING_REQUIRED`; do not guess from a village display name.
7. Supply a real HTTPS domain pointing directly to8.148.248.237 and a valid trusted certificate/full chain plus its private key, owned by the server admin and mode600. The activation tool validates SNI/hostname/system trust against a loopback TLS staging listener before stopping the old public HTTP container. It does not buy a domain, alter DNS, issue a certificate or assume service-provider/domain prerequisites have been completed.
8. Run the activation `--check`, then `--apply` with the same origin/certificate/key. It requires a snapshot taken within24hours, matching consolidated cloud acceptance, all existing file hashes, a fresh source metadata recheck and compatible live Workers. If the snapshot became stale before initial activation, prepare a new **uninitialized** target; never overwrite a target with new application writes. Source files that changed or disappeared block the consistency proof. Source updates after the recorded initial handoff are intentionally independent.
9. The tool starts a same-version TLS proxy privately on18443, checks its release and401 guard, enables the private bridge only after live readiness, and persists activation intent **before** changing public routing. Then it stops only the old Aliyun HTTP web container and exposes the new TLS route. It never restarts the shared PG or changes the GitHub Pages data connection. A failure after possible exposure retains the local database and stops for inspection; it never silently repoints new local writes to Supabase.
10. Public routing success is deliberately `public_route_enabled_pending_real_browser_and_gpu`, with `formal_complete=false`. In the actual HTTPS page verify login, space switching, survey/photo saves, group/personal planning, model upload/placement, scene milestone/reload/restore, and source-page independent writes. Then manually submit/read/import a4090 task and exercise the needed facade/provider path. Automated probes never create GPU/provider jobs or fees. Keep those real task IDs, byte digests and browser observations in the final private operator report. A disabled/unready provider is a reported missing feature, not a pass. Current tooling does not manufacture a formal-complete marker from an operator checkbox.

## Rollback and independent data

Prefer keeping the same Aliyun database and immutable files while rolling back code. The first unified release has no previous unified image to select automatically: `--rollback-code` stops its public route, retains local writes and does **not** restart the old Supabase-backed Aliyun page. Active private tasks must be drained or explicitly canceled before disabling the bridge. GitHub Pages remains independently writable throughout.

The generated `source-rollback-after-drain.sql` refuses to restore source RPC bodies while any private task history exists. Retain origin boundaries, task records and artifacts in that case; first disable new bridge submissions, drain/cancel active tasks under operator control, and perform a reviewed history-preserving rollback. If no private history was ever created, it disables the dedicated transport login and restores captured original function bodies. It never drops source tables/buckets/tasks/files or deletes copied data. Original ordinary source function grants were preserved by CREATE OR REPLACE.

Returning Aliyun ordinary business to Supabase requires an explicit difference/conflict report against the initialization snapshot. `difference_report` compares row IDs/content digests without overwriting either side and reports independent changes/conflicts; it is not an automatic merge. Do not simply replace the frontend configuration after local writes exist. Back up both sides, resolve conflicts per business object/geometry/file history, then review a concrete merge separately.

Unperformed gates remain visible: fresh real snapshot, real Linux image startup/cloud probe and load, source extension/Edge deployment, real Worker readiness, explicit village aliases where necessary, domain/certificate and actual HTTPS/GPU/provider browser acceptance. Never label this checklist or a synthetic CI run as a finished production migration.
