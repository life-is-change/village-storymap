# C2a 三维素材与版本预览：内部文件写入候选设计

状态：用户于 2026-10-18 确认本设计；尚未实现、构建镜像或部署。承接已确认的混合迁移设计及 2026-10-18 C1 云端验收。实施计划见 `docs/superpowers/plans/2026-10-18-scene-files-validation.md`。

## 目标与边界

用户希望普通业务逐步使用阿里云数据库和本地文件，保留 Supabase 及现有 4090 任务通道，并继续采用原目录 main → GitHub → 用户手动执行阿里云命令的流程。

这一子阶段让三维编辑器的自上传模型、贴图、素材组件和版本预览完成“上传 → 注册 → 放入方案 → 保存/版本 → 重启后授权读取”。不新增产品界面，不提前改变正式网站的数据来源。

C1 已验证的是内置元素方案；B2 已验证的是旧文件只读副本。二者均不包含新文件的写入生命周期。C2a 不等同于全部文件或业务迁移。

### 方案选择

1. **推荐：轻量业务 API + PostgreSQL + 服务器私有目录。** 复用现有候选架构，在事务中管理文件引用，流式处理文件；适合当前机器，避免新增完整对象存储服务。
2. 引入独立 S3 兼容对象存储服务：接口更通用，但增加进程、凭据、内存及运维面，目前无必要。
3. 全部普通文件写入一并迁移：同时涉及调查审核、照片与 GPU 输入上下文，范围过大，难以独立验收。

选择 1，先完成可独立验证的三维文件。`house-photos` 的新写入/删除、`group-models` 的旧模型库写入、`village-datasets` 的写入，以及 GPU 输入/输出桥接均保留后续阶段。B2 对这些旧文件的读取验收继续有效；不删除任何源文件。

## 已核对的现有接口

- `3D_scenes_edit/persistence/scene-edit-client.js`：场景项目、素材、组件相关 RPC；现有 API 客户端尚将素材/组件方法返回 `FILES_NOT_READY`。
- `3D_scenes_edit/assets/scene-asset-library.js`：模型标准化、原始/显示/低模/俯视图、多文件上传、注册与失败回滚；删除素材使用归档。
- `supabase_SQL/Scene Edit Studio.sql`：`scene_edit_assets`、`scene_edit_components`、版本预览以及既有权限函数和 RPC；发布/复制会产生共享同一物理文件的多条素材记录。
- `business-api/src/storage.mjs`：B2 用固定校验清单读取旧文件，不能直接作为可写目录索引。
- `business-api/scene/{contracts,database}.mjs`：C1 明确拒绝非 seed 引用和私有预览，需要新候选显式扩展，不能直接删除保护检查。

## 运行与数据隔离

- 沿用一个 PostgreSQL 容器，新增独立数据库 `village_scene_files_validation`；不覆盖 C1 的 `village_scene_validation` 或 A/B2 的 `village_copy`。
- 新候选 API `village-scene-files-validation-api` 仅发布 `127.0.0.1:18083`；新登录角色 `village_scene_files_login`，连接池最多 2，沿用经验证的用户身份与事务内 RLS。
- API 内存预算 256 MiB，文件上传最多 2 个并发；实现与云端验收需测量，预算不是容量结论。部署前验证可用内存、磁盘及原候选状态，不自动停止或重启现有容器。
- 私有状态 `~/village-scene-files-validation`；数据和文件均在网站目录/Git 之外，权限按现有私有副本规则校验。
- 从已校验归档恢复独立候选，应用候选 SQL；B2 已校验的 scene 桶旧文件只读接入，C2a 新文件单独落盘。原清单不改写，源 `storage.objects` 不承接新文件索引。
- 保留中断现场和 C1 成功候选，不执行删除卷、清空目录、重新覆盖已有数据库等操作。

## 文件和数据库的一致性

文件系统操作不具备数据库事务性，采用暂存与显式提交：

1. 认证后创建上传会话，记录用户、用途、课程/组或方案上下文、预计文件角色和字节上限。客户端提供一次性请求 ID；服务器生成会话 ID 与物理文件键，禁止客户端指定宿主机路径。
2. 以流式二进制请求写入私有临时文件，增量计数和 SHA-256；不将整个文件或 base64 正文载入内存。断线、超限、类型无效时不会生成可引用的业务素材。
3. 所有必需文件校验成功后，先持久化不可变文件，再在同一数据库事务中复核当前权限、调用固定业务 RPC 并登记逻辑引用，最后将会话标为已提交。事务失败的物理文件保留为不可见孤儿，供显式清理工具处理。
4. 提交超时后按同一请求 ID 查询结果，不自动重复创建素材；重试仅针对相同会话和相同内容，摘要或用户不一致则拒绝。
5. 未完成会话不会被读文件接口、场景保存或版本提交接受。启动检查能识别缺失文件并报错，不自动清库或伪造成功。

多文件角色包括原始模型、标准化显示模型、可选低模、可选低模原件和俯视图。必需文件缺失时整个素材不能提交；可选俯视图失败可沿用当前前端“无俯视图”状态，但不能登记不存在的路径。

## 类型、大小与引用契约

- 模型每文件不超过 50 MiB；纹理不超过 10 MiB；PNG 符号不超过 5 MiB；版本/组件预览不超过 10 MiB。会话的文件角色数和总字节由服务器依据用途计算上限，不能无限追加。
- 服务器验证大小、扩展名、MIME 和文件结构/签名，不依赖客户端检查。GLB 校验头、长度、JSON/BIN 分块和资源 URI，禁止外部 URL/文件依赖；服务端结构校验采用受限读取，避免 50 MiB 模型的全量复制。
- C2a 支持 GLB、PNG、JPEG、WebP。现有 SVG 符号暂返回明确的类型未支持错误，不以未审查的 SVG 作为可执行同源内容；SVG 处理后续独立补齐。
- 素材元数据中所有文件字段按白名单处理并必须属于同一已完成会话；原图、低模及俯视图不能借元数据引用别人的暂存文件或任意网络地址。
- seed 引用保留；私有引用解析为素材 UUID，经业务记录获得逻辑文件标识。场景保存、里程碑、组件、分支、恢复及提交均验证关联，禁止任意 URL/路径替代素材 ID。
- 组方案不得新增仅拥有者可读的个人素材引用；须先按已有业务规则发布/复制为该方案可见的课程/组素材。管理员私人沙盒可以引用其有权使用的个人素材。文件可见范围不能小于引用它的共享方案范围。

## 权限与文件读取

- Supabase Auth 保留，服务端在线验证原用户 UUID；不要求把 Secret key 或数据库密码写入浏览器。新用户/成员资料同步仍是正式切换前条件。
- 固定操作映射到已核对的素材/组件 RPC 和 SQL，不提供通用 SQL、表操作、任意 RPC 或任意文件系统代理。
- 注册、发布、复制、更新、归档沿用源权限规则；不能为了让管理员探测通过而绕开真实课程/成员要求。云端缺少测试上下文时明确报告缺失；若需构造新测试上下文，后续计划列出独立候选中的追加操作，不修改源或真实账号权限。
- 源 teacher/admin 广泛读取权限继续明确记录，不借迁移默默引入新的授课范围规则。跨学生、跨组、撤销成员的拒绝测试必须覆盖。
- 每次读取先重新授权，再取得可信文件映射；临时会话拥有权不等于已提交素材的永久读取权。不可通过其他人文件摘要、文件 ID 或路径绕过授权。
- 文件流支持有界 Range，返回准确内容类型、`nosniff` 和私有不缓存策略。前端用认证请求取得 Blob，再生成对象 URL；切换素材/退出时释放。GLB 自包含，不能凭外部贴图 URL 绕开认证。
- 旧 B2 清单中的 scene 文件仍逐个核验摘要及快照元数据。不能仅因数据库里存在旧路径便视为文件已复制。

## 归档与删除

“移出素材库”沿用逻辑归档。归档素材不能再从库中新放置；既有方案/组件和历史版本的合法引用继续可读，恢复时保留这些既有引用，不丢文件。

物理文件可能被发布副本、组副本、原始/低模变体或历史版本共同引用，因此不在素材归档时直接 unlink。独立清理命令默认只列数量/字节；实际清理只能处理过期且无引用的暂存/孤儿，并在锁定和再次核对后执行。C2a 不提供删除仍被业务引用的物理文件入口。

## 前端适配与发布

沿用当前素材库 UI、标准化算法、低模锚点和版本操作；新增显式注入的场景文件客户端与存储适配器，供测试使用。对授权失败、配额、网络中断、文件损坏和引用无效显示明确错误，不静默回退到 Supabase 写入。

C2a 内部验证完成前，不接入生产 `app.js` 路由，不替换全局 Supabase 客户端，也不公开 18083。未来浏览器真实整体验收使用受保护的本机隧道或已配置 HTTPS；不把登录令牌发送到公网 HTTP API。

## 验收与交付

1. 本地真实 PostgreSQL + HTTP + 文件系统：上传显示/低模/原件、登记、放置、保存、预览版本、分支/恢复、发布/复制/归档；新引用和历史引用均读回并核对摘要。
2. 负向验证：匿名/伪造身份、跨学生/跨组、撤销成员、混用会话、元数据路径注入、符号/硬链接、畸形 GLB、超限、Range、断线及重复提交。
3. 故障验证：上传中断、落盘后事务失败、响应丢失、进程重启、文件缺失；已成功的业务记录不指向未完成或不可验证的文件；有引用文件不能被清理。
4. 原 C1、B2、模型标准化和前端测试回归；记录代表性文件上传/下载时的内存、CPU、耗时及主机 available，不以空闲 stats 代替负载结果。
5. 本地提交 GitHub 后生成独立离线镜像、校验文件、部署及隐藏登录探测脚本。用户仅在本机完成的文件中选择确切文件名上传，再在阿里云拉取对应提交并执行命令。
6. 最终云端标记拟为 `SCENE_FILES_INTERNAL_VALIDATED_NOT_CUT_OVER`，只有真实上传/保存/版本/重启读回通过才写入验收；详细探测步骤需脱敏且能定位失败环节。

C2a 通过后仍需调查照片及其他业务写入、身份/权限同步、GPU 桥接、最新数据刷新、HTTPS 和正式切换。旧 Supabase 不会自动包含将来阿里云的新写入，不能视为持续同步的回退库。
