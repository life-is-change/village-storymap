# 阶段 3：小组方案空间与基线更新设计

**日期：** 2026-09-06  
**状态：** 已完成需求确认，待用户审阅  
**前置阶段：** 阶段 2 全班共享现状校核与冻结  
**适用范围：** 正式村庄、教学项目内已建立的小组及其 `group_plan` 空间

## 1. 背景与目标

阶段 2 允许全班在正式村庄的共享现状空间中持续校核，并由管理员在任意合适时间冻结不可变现状版本。阶段 3 以冻结版本为小组方案的统一底图，为每个教学小组提供一个长期存在、组内共享的方案空间。

本阶段不引入额外的“方案设计阶段”状态，也不要求教师在线分配对象。小组在线下协商分工，组员均可编辑建筑、道路和水体方案。后续出现新的冻结现状版本时，小组自行决定是否更新底图；更新采用三方合并，不覆盖已经形成的小组方案。

本阶段解决以下问题：

1. 冻结现状后，为已有小组自动建立唯一的小组方案空间。
2. 使用“冻结基线 + 稀疏方案覆盖”表达小组方案，避免为每个小组复制完整村庄数据。
3. 允许小组主动更新到新的冻结版本，并保留组内修改、冲突和恢复能力。
4. 统一二维和三维的小组方案上下文，同时保持管理员管理入口与个人空间列表分离。

## 2. 已确认的产品原则

1. 每个 `(teaching_project_id, village_id, group_id)` 只有一个活动的 `group_plan` 空间。
2. 多个冻结版本是同一小组空间的基线历史，不是多个可选择的小组空间。
3. 管理员冻结共享现状后，系统为当时已经存在的每个小组创建方案空间。
4. 冻结后新建立的小组，在首次需要方案空间时使用当前“推荐用于小组”的最新冻结版本创建。
5. 新冻结版本不会自动改变已有小组空间；小组可以继续使用旧版本，也可以主动更新。
6. 任一小组成员均可发起基线更新，但必须二次确认；管理员或教师也可代为执行。
7. 更新采用三方合并：未被小组修改的对象跟随新基线，小组已修改的对象保留；双方都修改同一对象时保留小组方案并创建冲突记录。
8. 冲突不会阻塞整个更新，也不会把小组空间变成只读。
9. 更新前自动创建恢复点；更新事务失败时，原基线和方案保持不变。
10. 小组方案允许增删改建筑、道路和水体；影像、村界和等高线仅作为只读参照。
11. 二维建筑属性和高度变化驱动三维白模；小组单体 GLB 模型仍按小组空间隔离。
12. 管理员可以管理所有小组方案，但这些空间不属于管理员个人空间，也不出现在管理员常规空间选择器中。

## 3. 空间生命周期

### 3.1 唯一空间

`planning_spaces` 中的 `group_plan` 使用教学项目、正式村庄和小组作为唯一业务身份：

```text
(teaching_project_id, village_id, space_type='group_plan', group_id)
```

同一小组更新基线时只修改该空间的 `base_snapshot_id`，不创建第二个空间。顶部选择器因此只显示“本小组方案空间”，不会出现 V1、V2 或多个历史小组空间。

### 3.2 冻结时创建

管理员成功冻结正式共享现状后，系统在同一受控流程中为项目内已有小组确保方案空间存在：

- 不存在：使用本次冻结快照创建空间并写入 `base_snapshot_id`。
- 已存在：保持其当前基线和方案不变。
- 重复调用：返回已存在状态，不产生重复空间。

冻结结果向管理员汇总“新建、已存在、失败”的小组数量。冻结快照本身必须成功且不可变；小组空间批量创建采用幂等的补偿式任务或可重试 RPC，个别小组创建失败不得制造重复空间，并在后台明确列入待重试项。

### 3.3 冻结后新增小组

课程中途新增小组时，系统查找该项目与正式村庄中最新且标记为 `recommended_for_groups` 的快照：

- 有推荐快照：创建唯一小组空间并绑定该快照。
- 没有冻结快照：只建立小组关系，方案入口显示“等待管理员冻结现状版本”。
- 后续产生推荐快照：管理员可重试创建，或学生首次进入时由安全 RPC 幂等创建。

米埗村等练习村庄不创建 `group_plan`。

## 4. 数据表达：冻结基线与稀疏覆盖

### 4.1 基线

`planning_spaces.base_snapshot_id` 指向不可变的 `feature_snapshots`。`feature_snapshot_items` 提供建筑、道路和水体的基线几何与属性，也可提供方案显示需要的只读参照关联。

### 4.2 小组覆盖

`planning_features` 不复制完整快照，只保存小组相对基线产生的变化：

- `added`：小组新建对象，使用新的稳定对象编码。
- `updated`：覆盖同一基线对象的几何或属性。
- `deleted`：保存删除墓碑，使基线对象不再出现在解析结果中。

覆盖行至少具有完整项目、村庄、空间、小组、图层、对象编码、来源基线对象编码、操作类型和修订号。删除不得物理删除历史覆盖行。

### 4.3 统一解析结果

二维地图、三维白模、统计和导出不自行拼接数据，而是通过统一解析接口得到：

```text
resolved group plan = active baseline items + latest group overrides
```

解析规则：

1. 没有覆盖的基线对象按基线显示。
2. `updated` 使用小组覆盖替换基线版本。
3. `deleted` 隐藏基线对象，但保留墓碑与历史。
4. `added` 追加为小组对象。
5. 同一对象只返回一个当前有效结果。

服务端 RPC 是事实解析入口，前端只负责缓存和渲染，不能因本地缓存遗漏删除墓碑。

## 5. 小组编辑规则

### 5.1 可编辑图层

- 建筑：新增、修改几何、修改属性、删除。
- 道路：新增、修改几何、修改属性、删除。
- 水体：新增、修改几何、修改属性、删除。
- 影像、村界、等高线：只读参照，不在阶段 3 形成方案覆盖。

所有组员都可以编辑三类方案对象，不设置线上负责人、任务分配或认领流程。

### 5.2 对象协作

日常编辑沿用阶段 2 的对象短锁和乐观修订校验：

- 进入几何编辑前获取短时锁并持续续期。
- 保存必须携带读取时的预期修订号。
- 锁冲突或修订冲突时拒绝覆盖并重新加载对象。
- 属性、几何、删除、照片、问题和讨论分别保留操作者及历史，但均使用同一项目、村庄和小组空间上下文。

阶段 2 的“几何校核后才允许属性、照片、问题和讨论”是现状校核规则。小组方案对象不存在 `pending` 校核门禁；组员可以按方案工作需要编辑允许的数据。

### 5.3 二维与三维

- 二维和三维读取同一 `group_plan` 解析结果。
- 建筑层数或高度变化后，三维白模按现有规则重新计算。
- 道路和水体主要在二维编辑，保存后在三维场景同步显示。
- 小组上传的单体 GLB 模型继续由既有小组模型库管理，不改变白模数据，也不能跨小组读取。
- 单体模型失效时回退显示白模，不阻塞二维编辑。

## 6. 基线更新与三方合并

### 6.1 更新入口

小组空间的“方案基线”模块显示：

- 当前基线版本与冻结时间；
- 当前推荐的最新版本；
- 新增、修改、删除对象数量摘要；
- “查看更新内容”和“更新基线”操作；
- 更新历史、恢复点及未解决冲突数量。

任一组员可查看差异并发起更新。执行前必须二次确认，并提示更新期间小组空间会短暂锁定。

### 6.2 三方输入

更新使用：

- 旧基线 `B0`；
- 小组在 `B0` 之上的当前方案 `G`；
- 目标新基线 `B1`。

对象以不可变系统对象编码匹配，不使用建筑编号、道路名称等可编辑业务字段作为关联键。

### 6.3 合并规则

| 旧基线到新基线 | 小组相对旧基线 | 结果 |
| --- | --- | --- |
| 未变化 | 未修改 | 使用新基线对象 |
| 已变化 | 未修改 | 跟随新基线 |
| 任意 | 小组新增 | 保留小组新增对象 |
| 未变化 | 小组修改或删除 | 保留小组覆盖 |
| 新基线修改或删除 | 小组也修改或删除同一对象 | 保留小组覆盖并创建冲突 |
| 新基线新增 | 小组无同编码对象 | 纳入新基线 |

若极少数情况下新基线新增对象编码与小组新增对象冲突，保留小组对象、记录编码冲突，并要求后续人工处理。

冲突只标记需要复核，不阻止小组继续编辑。解决冲突时可以选择保留小组方案、采用新基线，或在地图上形成新的人工合并结果；所有选择均追加历史。

### 6.4 原子更新

基线更新 RPC 执行以下步骤：

1. 从 `auth.uid()` 确认组员或管理员身份。
2. 锁定目标 `planning_spaces` 行并校验期望基线 ID。
3. 检查空间更新锁和仍有效的对象编辑锁。
4. 创建更新前恢复点。
5. 计算并写入必要的覆盖调整与冲突记录。
6. 把 `base_snapshot_id` 更新为目标快照。
7. 写入更新事件和统计摘要后提交。

任何一步失败都整体回滚。两个并发更新只允许一个成功，另一个返回 `BASELINE_VERSION_CONFLICT`。如存在活动对象锁，返回 `GROUP_SPACE_BUSY`，不强制清理他人的编辑状态。

## 7. 历史、冲突与恢复

建议新增以下职责明确的结构：

- `group_baseline_updates`：记录旧基线、新基线、操作者、时间、状态和统计。
- `group_baseline_conflicts`：记录更新批次、图层、对象编码、冲突类型、两侧摘要、解决状态与解决结果。
- 恢复点：复用或扩展既有快照/版本结构，保存更新前的基线 ID 与稀疏覆盖状态引用。

恢复操作不是修改旧历史，而是建立新的恢复批次，把空间恢复到选定恢复点所代表的基线与覆盖状态。只有管理员或教师可以执行整空间恢复；普通组员可查看恢复点但不能执行。恢复同样需要空间级锁、二次确认和完整事务。

## 8. 学生端界面

### 8.1 顶部空间选择器

学生在正式村庄中最多看到：

- 我的个人体验空间；
- 全班共享现状空间；
- 本小组方案空间。

“本小组方案空间”仅在学生已经加入小组且存在冻结基线后出现。显示类似“组内共享 · 基线 V1.0”的辅助状态，不把每个基线版本显示成独立空间。

无小组时提示先加入小组；尚无冻结快照时提示等待管理员冻结。个人体验数据和全班共享现状数据不得混入小组方案。

### 8.2 方案基线模块

模块位于小组空间的项目设置或空间信息区域，提供当前基线、可用更新、差异摘要、更新历史、恢复点和冲突列表。冲突可在地图定位，但不在顶部工具栏增加大量筛选项。

更新成功后通过实时事件通知其他组员重新拉取事实数据；断线重连后也必须完整重载当前基线、覆盖和冲突状态。

## 9. 管理员后台

管理员后台增加“小组方案”管理区域，按教学项目和正式村庄列出：

- 小组名称与成员数；
- 方案空间是否存在；
- 当前基线与最新可用基线；
- 最近编辑时间；
- 未解决冲突数量；
- 创建失败或更新异常状态。

管理员可以从列表执行：

- 为缺失小组补建方案空间；
- 进入某小组的方案管理视图；
- 代为更新基线；
- 查看冲突与操作历史；
- 恢复到更新前的恢复点。

“进入小组方案”只建立临时管理上下文。所有小组方案空间不属于管理员的个人空间，也不加入管理员普通工作区的空间下拉列表。退出管理视图后返回后台列表。管理员操作必须写入活动日志，并在 RPC 中再次校验角色和目标项目范围。

## 10. 权限与安全

- 小组成员只能读取和修改自己小组的 `group_plan` 数据。
- 其他学生不能读取该小组尚未发布的方案、模型、冲突或更新历史。
- 教师和管理员可以读取所属管理范围内全部小组方案，并执行代更新与恢复。
- 匿名用户和非项目成员不能读取或写入阶段 3 数据。
- 学生不能直接更新 `base_snapshot_id`、恢复点、冲突状态或更新批次，只能调用安全 RPC。
- `security definer` RPC 固定安全 `search_path`，撤销 `anon` 和 `public` 执行权限，并从 `auth.uid()` 推导操作者。
- RLS 和 RPC 均校验教学项目、正式村庄、空间类型与小组成员关系，不能只凭 `space_id` 授权。
- 客户端提供的 `user_id`、`group_id` 或管理员标志不能作为授权事实。

## 11. 错误与恢复策略

- **尚无基线：** 不创建空白方案空间，显示等待冻结状态。
- **重复创建：** 返回已有唯一空间，不创建副本。
- **空间繁忙：** 有活动对象锁或正在更新时拒绝基线更新，提示稍后重试。
- **版本冲突：** 期望基线已变化时拒绝本次更新并刷新摘要。
- **合并失败：** 更新事务全部回滚，旧基线和小组覆盖不变。
- **部分冲突：** 更新仍可成功，冲突进入列表并默认保留小组覆盖。
- **实时断线：** 暂停共享写入；恢复连接后先完整拉取事实数据。
- **恢复失败：** 当前空间不变，失败事件写入管理员日志。
- **三维加载失败：** 回退白模或提示模型不可用，不阻塞二维方案。
- **批量建空间失败：** 后台列出失败小组并允许幂等重试，不产生重复记录。

## 12. 测试与验收

### 12.1 数据库契约

- 同一项目、村庄、小组最多一个 `group_plan`。
- 练习村庄不能创建小组方案空间。
- 冻结后为已有小组幂等创建空间，不修改已有空间基线。
- 新小组正确绑定推荐快照；无快照时不生成无基线空间。
- 稀疏覆盖的新增、更新、删除墓碑约束有效。
- 学生不能直接改变基线、冲突或恢复记录。
- RLS 拒绝跨小组、跨项目、跨村庄及匿名访问。

### 12.2 解析与编辑

- 基线对象、更新覆盖、删除墓碑和新增对象解析为唯一当前结果。
- 建筑、道路和水体均可新增、修改、删除。
- 影像、村界和等高线保持只读。
- 两人编辑同一对象时，锁和修订校验阻止覆盖。
- 二维保存后，三维白模和道路、水体显示读取相同事实。
- GLB 模型仍严格按小组隔离，模型失败时白模可用。

### 12.3 基线更新

- 未修改对象跟随新基线。
- 小组已修改或删除对象保持不变。
- 双方同时变化时保留小组覆盖并生成冲突。
- 冲突不阻止非冲突对象更新，也不锁死空间。
- 并发更新只有一个成功，失败请求不产生半成品。
- 更新前恢复点完整，管理员恢复会形成新的历史批次。

### 12.4 界面与回归

- 学生空间选择器只显示本人可用的三个逻辑空间，不显示多个基线版本。
- 管理员普通空间选择器不包含所有小组空间。
- 管理员后台能查看、进入、代更新和恢复任意小组方案。
- 无小组、无冻结快照、空间繁忙和更新失败均有明确空状态或错误提示。
- 阶段 1 多村庄切换、阶段 2 共享校核与冻结、个人体验空间及现有 2D/3D 功能不退化。

### 12.5 本阶段验收边界

本阶段完成代码、迁移、自动化测试以及可安全执行的远程数据库部署。按照已确认安排，正式村庄真实数据、多个真实学生账号、多人并发和完整教学流程验收统一延后到全部阶段完成后进行。

因此阶段 3 完成时应标记为：

```text
功能与数据库部署完成；真实教学数据总体验收待后续统一执行。
```

不得为了提前通过阶段 3 而向正式项目伪造村庄、小组或学生业务数据。

## 13. 非目标

- 新增独立“方案设计阶段”状态机。
- 教师在线分配对象、学生领取任务或对象认领。
- 为每个冻结版本创建一个新的小组空间。
- 自动把新基线强制推送到已有小组。
- 把完整冻结快照复制到每个小组的 `planning_features`。
- 允许学生查看其他小组的未发布方案。
- 让管理员所有可管理的小组空间出现在普通空间选择器中。
- 在本阶段实现最终成果提交、公开发布、评价、评分或方案对比展示。

## 14. 推荐实施边界

实施应拆为以下连续能力：

1. 数据表、唯一约束、RLS 与小组空间生命周期 RPC。
2. 冻结后的幂等空间创建及新小组补建。
3. 稀疏覆盖解析、三类图层编辑与二维/三维统一读取。
4. 基线差异预览、恢复点、三方合并和冲突处理。
5. 学生端“本小组方案空间”和方案基线模块。
6. 管理员后台“小组方案”列表与临时管理视图。
7. 自动化测试、远程迁移、安全检查与回归。

实现时优先复用现有 `planning_spaces`、`planning_features`、对象锁、版本历史、冻结快照和小组模型库，不建立功能重复的第二套编辑系统。
