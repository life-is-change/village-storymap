# 三尺度工作室与公共场景编辑器设计

## 1. 背景与目标

平台新增三个面向不同小组的独立研究模块。三个模块在课程叙事上形成“微观—中观—宏观”的尺度关系，但不是必须依次完成的关卡：每个小组选择一个方向即可形成完整成果，也可以自愿体验其他模块。

| 尺度 | 工作室 | 研究对象 | 主要成果 |
| --- | --- | --- | --- |
| 微观 | 建筑更新工作室 | 单栋建筑、立面、材质与替换模型 | 建筑改造模型与说明 |
| 中观 | 公共空间工作室 | 广场、街巷、滨水和其他公共空间 | 二维方案、三维场景与版本对比 |
| 宏观 | 村庄营造实验室 | 村庄整体布局、资源与发展策略 | 游戏化村庄方案及发展结果 |

当前优先建设中观的公共空间工作室。微观模块基本沿用现有建筑模型上传、替换、姿态调整和照片立面工作流，只补入口与成果接口。宏观模块后续建设为轻量的《江南百景图》式村庄营造体验，不作为本期依赖。

## 2. 教学组织原则

三个模块采用“并列独立、可选互通”模式：

- 任何模块均无前置模块。
- 每个模块均提供可独立完成任务的基础素材和数据。
- 建筑更新成果可自愿发布为公共空间工作室的建筑资产。
- 公共空间组合可自愿发布为村庄营造实验室的场景组件。
- 教师可以指定方向或由小组自选，但日常体验不依赖教师审批。
- 最终可联合展示三个尺度的成果，不要求把它们合并为同一方案。

底层可以复用身份、小组权限、素材元数据、版本和成果提交能力；这种技术复用不改变教学上的独立性。

## 3. 模块二产品定位

模块二是面向公共空间设计的“场景装配编辑器”，不是单纯素材摆放器，也不尝试在浏览器中重做完整 Photoshop、SketchUp 或 Blender。

它吸收三类能力：

1. PS 式场景管理：图层、锁定、隐藏、多选、框选、复制、成组、对齐、等距分布、撤销和重做。
2. SU 式基础构建：捕捉、尺寸输入、测量、移动、旋转、缩放、绘制面并设置高度，以及沿线生成矮墙、路缘、绿篱和栏杆。
3. 外部模型导入：复杂亭廊、雕塑、设施和定制景观由学生在 SU/Blender 中制作，导出 GLB 后上传并参与组合。

平台应能独立完成广场、道路、铺装、绿地、水面、树阵、设施和基本构筑物等常见公共空间搭建。异形曲面、精细建筑建模和专业渲染继续交给外部软件。

## 4. 学生工作流

1. 学生进入真实村庄，漫游地图或查看系统提供的建议点。
2. 学生自由绘制公共空间研究范围。建议点只提供灵感，不是强制任务。
3. 系统检查范围是否位于项目边界内、是否超过面积上限、是否不合理覆盖现状建筑主体。
4. 系统固定当前现状版本，创建本组独立的场景方案空间。
5. 学生在二维视图中绘制点、线、面并组合素材。
6. 学生随时切换三维视图检查尺度、遮挡、高度和空间感，并对离散对象进行三维微调。
7. 系统持续自动保存草稿；学生主动创建“初步构思”“中期方案”“最终方案”等里程碑。
8. 学生比较现状与方案或任意两个版本，选择一个版本提交并生成成果截图和说明。

## 5. 空间隔离与二三维同步

### 5.1 只读基线与差异方案

现状空间永久只读。模块二不完整复制影像、建筑、道路和地形，而是创建逻辑方案空间：

- 固定基线空间标识及版本号；
- 保存本组新增、修改和删除的差异对象；
- 每个小组、每个选区和每条方案分支相互隔离；
- 基线后续更新不会暗中改变既有方案；如需升级基线，必须创建显式的新方案分支。

这既避免污染现状，也避免大量重复数据和基线漂移。

### 5.2 单一场景文档

二维和三维不是两份独立数据。统一场景文档是唯一事实来源，二维与三维只是不同编辑视图：

| 三维操作 | 二维结果 |
| --- | --- |
| 水平移动 X/Y、绕竖轴旋转 | 立即更新二维位置和朝向 |
| 水平缩放、复制、删除、分组 | 立即更新占地框和对象关系 |
| 高度偏移 Z、对象高度 | 二维位置不变，属性面板显示高度标记 |
| 俯仰、横滚、材质细节 | 平面几何不变，保存为三维扩展属性 |
| 铺装边界、步道中心线、种植范围 | 首期仅在二维编辑，随后重新生成三维表达 |

所有用户操作都转换为统一命令，再同时驱动场景文档、撤销历史、二维渲染、三维渲染与自动保存。

## 6. 场景对象模型

模块二以多类场景要素为主体，建筑只占少量：

### 6.1 面状要素

- 铺装、草坪、水面、花坛、种植区和活动场地；
- 支持任意多边形、材质比例、标高和基础拉伸；
- 二维编辑边界，三维生成表面或低矮体块。

### 6.2 线状要素

- 步道、道路边线、路缘、矮墙、栏杆、绿篱和排水沟；
- 支持宽度、高度、端点吸附和节点编辑；
- 三维可沿路径重复或拉伸指定截面/资产。

### 6.3 点状资产

- 树木、灌木、座椅、桌子、灯具、垃圾桶、标识、雕塑和健身设施；
- 支持位置、朝向、尺寸、高度、复制、阵列和随机轻微变化；
- 重复资产采用实例化渲染。

### 6.4 小型构筑物与少量建筑

- 亭、廊架、公交站、摊位、小舞台和儿童设施；
- 主要通过 GLB 上传、平台基础资产或小组共享组件获得；
- 详细建筑建模仍由模块一或外部软件负责。

### 6.5 组合组件

学生可把多个要素保存为可复用组件，例如树池座椅、廊架花池、儿童活动角、村口节点或滨水平台。组合后仍可解组和编辑，不合并成不可修改的大模型。

## 7. 工具范围

首期必须支持：

- 选择、框选、多选、移动、旋转、缩放、复制、删除；
- 图层显示、隐藏、锁定和排序；
- 成组、解组、对齐和等距分布；
- 网格、端点、边线、中心和现状要素吸附；
- 距离、角度、面积和对象尺寸显示；
- 绘制点、折线、多边形和矩形；
- 面状要素设置材质与简单高度；
- 线状要素设置宽度、高度和重复资产；
- 点状与 GLB 资产放置；
- 组合组件保存与复用；
- 撤销、重做、自动保存和里程碑版本。

后续再考虑复杂地形塑造、挖填方、日照/雨洪模拟、多人实时同屏编辑、复杂网格建模和在线外部模型市场。

## 8. 素材体系

采用“基础预设 + 小组上传 + 组合资产 + 可选课程共享”的四层素材体系。

1. 平台基础库只保证开箱可用，不承担最终效果上限。
2. 小组素材库保存本组上传的 GLB、地面纹理和二维符号。
3. 组合资产库保存本组制作的可拆分场景组件。
4. 学生可主动把优秀组件发布到课程共享库；其他组复制后使用，不能修改原件。

支持格式：

| 类型 | 格式 | 用途 |
| --- | --- | --- |
| 地面材质 | PNG、JPG、WebP | 铺装、草地、水面和种植区 |
| 独立物体 | GLB | 植物、家具、灯具、小品和构筑物 |
| 二维符号 | SVG、PNG | 缺少三维模型时的二维表达 |

上传 GLB 后自动生成俯视缩略图、读取尺寸、创建二维占地框并检查文件体积、贴图尺寸和复杂度。学生可校准真实尺寸、朝向和落地点。

平台自带素材随代码保存在 `3D_scenes_edit/assets/seed/`。学生上传文件进入 Supabase Storage，不进入 Git 仓库。

## 9. 保存、版本与异常恢复

- 每次操作先写入浏览器本地状态；约 1 秒防抖后同步小组草稿。
- 断网时操作进入本地队列，网络恢复后按修订号继续同步。
- 里程碑包含名称、说明、修改者、时间、缩略图和完整场景快照。
- 从旧版本恢复时复制为新草稿，不覆盖历史版本。
- 并发修订冲突时保留两个副本，不静默覆盖。
- GLB 加载失败时二维保留占位符和布局数据。
- 单个上传失败或三维预览失败时，二维编辑仍可继续。
- 被场景版本引用的素材采用归档/软删除，不能因素材库删除而破坏历史成果。

## 11. 历史构建器恢复与借鉴策略

### 11.1 来源

恢复两份相互独立的只读参考副本：

1. Git 删除前版本：提交 `008893caff37b0f6297ebc04318c8a5580b81685` 下的 `building-assembler/`。
2. 增强备份版本：`E:\研究生工作\332工作\3D村庄规划网页\village-storymap聪0526\building-assembler\`。

每份副本均保留 `assembler.js`、`index.html`、`style.css` 和 `components-library.json`，并附带来源清单、文件大小和 SHA-256 校验值。

### 11.2 非覆盖要求

- 仅向 `3D_scenes_edit/legacy/` 新增副本；
- 不恢复原来的根目录 `building-assembler/` 路由；
- 不覆盖当前平台、当前模型工作流或原备份目录中的任何文件；
- 不把旧版直接作为生产入口；
- 正式代码通过测试驱动的逐项移植获取能力，不通过整体复制后原地修改。

### 11.3 借鉴范围

两版共同提供 Three.js 场景、相机、射线拾取、拖动、网格吸附、旋转、放置、删除、基础碰撞、撤销和父窗口通信思路。

Git 删除前版本作为最小框架基线；0526 版本用于补充范围绘制、尺寸显示、旋转后占地计算、承托/约束、属性编辑和更完整的快照逻辑。建筑专用的楼层、墙体、屋顶和楼板支承规则不进入通用场景核心。

旧代码使用 Three.js 0.128 CDN、全局状态、通配 `postMessage`、有限撤销且缺少测试，因此只能作为参考，不直接上线。

## 12. 数据与权限边界

建议的数据职责为：

- `scene_edit_projects`：选区、基线引用、小组、状态和当前修订；
- `scene_edit_objects`：点线面几何、资产引用、变换、样式、图层与分组；
- `scene_edit_assets`：素材元数据、Storage 路径、许可信息、尺寸和可见范围；
- `scene_edit_components`：可拆分组合组件定义；
- `scene_edit_versions`：不可变里程碑快照、缩略图与提交状态。

所有表使用教学项目、村庄、小组和空间进行范围约束，并启用行级权限。小组私有内容仅本组成员可修改；课程共享内容可读但只能复制；教师拥有查看和必要的下架权限，不需要审批每次上传或选区。

## 13. 性能目标

首期以单场景约 300 个对象、50 个独立 GLB 资产为设计上限。相同树木、灯具、座椅等采用实例化；模型、纹理和缩略图按需加载并缓存。超过建议复杂度时给出可理解的优化提示，不直接损坏方案。

## 14. 测试与验收

### 14.1 自动化测试

- 场景命令：选择、移动、旋转、缩放、复制、删除、成组、撤销和重做；
- 几何规则：吸附、边界限制、尺寸、面积、旋转占地和碰撞；
- 转换一致性：二维场景文档到三维表达及允许的三维操作回写；
- 保存恢复：防抖保存、断网队列、修订冲突、里程碑创建与恢复；
- 素材生命周期：上传校验、缩略图、引用、分享复制和软删除；
- 权限：不同教学项目、村庄、小组和角色之间的数据隔离；
- 历史恢复：两份旧版本校验值及来源清单稳定，当前文件不被覆盖。

### 14.2 浏览器验收

- 学生能自由选区并创建不污染现状的方案；
- 学生能用点、线、面和 GLB 完成一个基本公共空间；
- 二维操作能正确出现在三维，三维允许的变换能回写二维；
- 学生能上传座椅、树木等素材并保存组合组件；
- 刷新、短时断网、模型加载失败后方案仍可恢复；
- 小组之间不能修改对方私有方案和素材；
- 学生能创建版本、前后对比并提交成果；
- Chrome 和 Edge 桌面端在目标复杂度下保持可操作。

## 15. 实施顺序边界

正式实施计划应优先完成：

1. 非覆盖恢复两份历史构建器并建立来源清单；
2. 建立独立 `3D_scenes_edit/` 骨架和统一场景文档；
3. 完成只读基线、逻辑方案空间和自动保存；
4. 完成二维点线面编辑与图层/变换命令；
5. 完成通用 GLB 素材上传、放置和组合；
6. 完成三维预览及受控的三维回写；
7. 完成版本比较、提交、权限和性能验收。

模块一的重构和模块三的游戏化实现均不属于模块二首期计划。
