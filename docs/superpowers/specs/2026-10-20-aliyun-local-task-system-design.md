## 2. 采用的架构

网页 → 同源阿里云Auth/API → PostgreSQL、私有文件
校园4090 Worker → 主动HTTPS请求阿里云API → 领取/续租/状态/文件
阿里云API → 网页SSE/有界轮询 → 进度和完成通知

复用已实现的普通业务API、权限、场景、文件存储、连接池和大部分前端任务接口；新增本地认证服务、本地任务调度及Worker网关。旧Supabase网关保留为兼容模式，默认不因代码更新切换运行环境。已完成的旧镜像保留，不能复用其版本标签声称为本方案。

不在2GB机器运行全套Supabase；采用成熟的开源Supabase Auth（GoTrue）独立服务加既有PostgreSQL/API/Nginx，复用兼容的Auth协议，不自写密码校验和签发流程。固定服务版本/镜像摘要须与实际源auth schema及迁移版本验证匹配，不能凭最新版标签启动。任务领取与续租用PostgreSQL原子事务/行锁与租约；不新增Redis/RabbitMQ或本地GPU推理服务。任务等待、文件传输和SSE不长时间占用数据库连接。

## 2.1 本地认证、密码与身份归属

### 迁移契约

- 迁移源 `auth.users`、必要的identities及兼容的相关用户记录，保留每个用户UUID、现有密码哈希和学号合成邮箱映射；`profiles`、照片、操作记录、组员与模型/任务所有者继续引用原UUID。不能删除重建用户、按名字或相同邮箱错误认领旧数据，也不能生成新UUID后遗留旧外键。
- 检查源schema、Auth迁移版本、密码哈希格式及目标Auth服务兼容性；先在隔离目标验证，不直接对原Supabase执行DDL。普通用户权限角色由本地profiles/成员关系判断，新注册不能自授teacher/admin。
- 原数据库副本中“只插入auth.users(id)”的身份锚点逻辑不再作为本地注册方案。本地Auth创建真实用户，再由受控的事务化资料初始化创建profiles；并发注册、初始化失败和重试不得产生两个用户或提升权限。旧托管用户触发器按目标Auth部署重新审计，不能盲目复用或全部丢弃。
- 密码仅隐藏录入用于真实验收，不导出明文。不要求用户为迁移重设密码，但原密码能否工作必须通过真实目标服务登录确认，不能根据表行数宣称保留成功。
- 不继承源站JWT签名密钥，不把复制来的refresh token、会话或短期验证/找回令牌当作本地有效会话；新旧站点令牌严格隔离。首次阿里云登录重新建立本地会话，不影响原站登录；相同用户UUID不意味着源JWT可以访问本地API。
- 如果盘点发现实际启用OAuth、MFA或其他加密身份数据，明确验证其配置/密钥迁移条件，不能静默删除、绕过MFA或称功能已完成。当前已确认主入口是学号+密码，不凭空新增第三方登录。

### 服务边界

- 公共认证入口与网站同源 `https://8.148.248.237/auth/v1/`，由Nginx反向代理固定内部Auth服务。Auth/数据库不直接暴露额外公网端口；数据库使用Auth专用受限登录，运行时不能使用超级用户，schema迁移权限与运行权限分离。
- 网页Auth客户端、首页、主应用、管理页、场景和生成器必须从不可变部署配置选择站点Auth端点及独立存储键。GitHub Pages仍保留原Supabase端点；不接受URL/localStorage任意改Auth源或信任来源声明。
- 本地API只信任明确配置的本地issuer/audience/算法/签名来源，核验过期、禁用、用户存在及适用的会话撤销状态；不能只解码JWT。若采用本地Auth在线核验，走受控内部网络，不再往返东京；若使用签名公钥核验，必须同时保留本地禁用/撤销策略并测试，不能降低权限边界。
- 注册、登录、刷新、登出、资料就绪、管理账号停用及权限判断都应在阻断原项目 `rzmbmwauomzwiyenafha.supabase.co` 的情况下通过。日志/网页/API返回不得泄露密码哈希、refresh token、签名私钥或Worker凭据。
- Auth密码学及协议使用成熟服务。额外认证容器的内存与连接池单独计量，纳入整机容量；不把“没有全套Supabase”当成2GB一定足够的保证。

### 账号恢复范围

当前 `auth-system.js` 使用学号合成邮箱注册/登录，没有实现可直接沿用的用户邮件找回密码UI。因此，不将购买SMTP或绑定真实邮箱设为现有登录流程迁移的前提，也不宣称合成邮箱能收找回邮件。

设计采用管理员在核实身份后发起本地受控密码重置，必须有管理员再认证、限流、审计、会话撤销及防越权验证；实现接口/操作形态在实施计划中明确，不能公开无验证重置接口。若要增加真实邮箱自助找回，需要另外确认真实收件地址和发信服务，在配置齐全前明确标为未提供。改密码不改变UUID和历史文件/记录归属。

## 3. 队列、授权与数据一致性

- 分图底、立面任务类别；客户端固定操作接口，提交编号与身份/上下文/输入摘要绑定，丢响应重放不得重复生成任务。

- 领取使用原子SKIP LOCKED和服务端lease token；进度、续租、上传与完成均核对有效租约及任务归属，过期Worker不能覆盖新Worker结果。保留取消、重试、幂等完成、过期回收和最大尝试数。
- 本地队列只接受明确的新本地任务。新快照中的旧Supabase队列表仅作历史参考，不能启动消费者重放已有/运行中/计费任务。
- Worker只访问固定HTTPS源和固定文件ID接口；不接受任意URL/路径。下载校验类型、大小、摘要，上传流式写入私有暂存，完整文件验证后原子提交；失败保留可检查状态并清理无引用暂存，绝不删除已引用结果。
- 图底结果导入使用本地任务ID、产物摘要及目标个人空间幂等收据；生成物展示和导入检查当前权限，拒绝越权、失效项目/空间、重复应用和旧响应。
- 立面原有矫正→裁切确认→生成→文件展示流程保留；输入照片、任务状态、生成版本和结果均属于阿里云。断线重试不产生重复任务或错误完成。
- 既有云端立面提供商功能若在当前页面启用，其任务控制/结果也本地管理，提供商调用由阿里云后端完成；密钥只在服务端隐藏录入，计费请求的未知结果不得自动重提。真实付费验收仍需用户明确授权，未验证时不能记全流程通过。

1. **本方案：独立本地Auth + 现有API/文件/任务 + PostgreSQL**。符合原Supabase仅作为保留环境的目标，可复用旧用户密码与客户端Auth协议；代价是需要验证Auth schema版本、迁移权限、资源与注册/撤销/恢复流程。优先采用。
2. **全套自托管Supabase**。服务兼容面较全，但官方当前给全组件最低4GB、推荐8GB+，不符合现有2GB机器的资源边界，不能直接搬全套容器声称合适。参考 https://supabase.com/docs/guides/self-hosting/docker 。
3. **继续托管Auth或自写密码系统**。前者保留在线原站依赖，不符合本次明确目标；后者引入额外认证安全及兼容成本，本次不采用。

“全流程迁移”指原Supabase承担的平台身份/业务/存储/队列/状态服务在阿里云自主运行；第三方底图、Cesium资源、外部AI提供商仍属于原功能固有外部服务，校园GPU仍由4090计算。不能宣称整个应用完全离线或阿里云CPU执行所有模型。

书面设计自检：保留原UUID与哈希但不继承源会话；账号恢复不依赖虚构邮箱；普通/任务/文件引用同一本地身份；原站不修改；新站有独立持续备份；IP HTTPS与校内主动取任务方向一致；2GB容量和源Auth版本保留为实测门槛。本文只定义契约，实施计划与实际代码尚未完成。
