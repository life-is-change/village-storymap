# 阶段 2：全班共享现状空间校核与冻结设计

**日期：** 2026-09-04  
**状态：** 已完成需求确认，待用户审阅  
**前置阶段：** 多村庄双轨空间体系与本地 V0 数据包流程  
**适用空间：** 正式村庄的 `formal_shared` 全班共享现状空间

## 1. 背景与目标

阶段 1 已建立“教学项目—村庄—空间—数据版本”的上下文，并允许管理员为正式村庄发布原始 V0。V0 是从建筑识别、OSM 和 DEM 等来源得到的初始数据，不要求管理员在发布前逐个修正。

阶段 2 由全班学生共同校核正式村庄的现状数据。学生直接在同一个共享现状空间中确认或修改建筑、道路和水系几何；某个对象的几何完成校核后，全班才可继续处理该对象的属性、照片、问题和讨论。管理员在合适时间把当前状态冻结为不可变版本，供阶段 3 的小组方案空间作为统一底图。

本阶段解决三个核心问题：

1. 用明确而轻量的状态区分“尚未处理”和“已经处理”的对象，减少重复劳动。
2. 允许全班即时协作，同时通过对象锁、版本校验、完整历史和可恢复操作控制并发风险。
3. 在不停止共享现状继续更新的前提下，形成稳定、可追溯的小组规划底图。

## 2. 已确认的产品原则

1. 全班共同编辑一个正式村庄的共享现状空间，不建立线上任务分配、领取或认领机制。
2. 学生在线下协商并大致分工，但任何学生仍可处理其他对象。
3. 几何校核是对象进度的主轴；属性、照片、问题和讨论不分别计入主进度。
4. 对象几何尚未校核时，属性编辑、照片上传、问题报告和讨论均被禁止。
5. 几何校核状态属于共享对象：任一学生完成后，对该对象的后续功能向全班开放，而不是只对操作者开放。
6. 学生保存后直接更新共享现状，不建立教师逐条审批队列。
7. 共享现状空间依靠短时对象锁和乐观版本校验避免覆盖，并保留完整修改历史。
8. 管理员冻结的是某一时刻的不可变快照，不把正在工作的共享现状空间锁为只读。
9. 后续冻结 V2、V3 时，不自动替换已经使用旧版本的小组空间底图；由管理员显式决定是否升级或重建。
10. 阶段 2 首版逐要素校核范围只有建筑、道路和水系；等高线保留既有编辑、删除能力，但不进入校核进度。

## 3. 对象身份与校核状态

### 3.1 不可变技术标识

建筑、道路和水系对象使用不可变的系统对象编码作为关联主键。建筑编号、道路名称、户主、层数、高度和结构等均为可编辑业务属性，不能作为数据库关联键。

- V0 对象在发布时生成稳定的系统对象编码，并在共享空间、历史记录和冻结快照中持续沿用。
- 学生新增对象在首次成功保存时由服务端生成系统对象编码。
- 删除使用软删除，不回收或复用对象编码。
- 任何客户端不得自行指定、伪造或更换系统对象编码。

### 3.2 几何校核状态

`geometry_status` 采用以下受控值：

| 状态 | 含义 | 是否计入 V0 已校核 | 是否开放对象后续操作 |
| --- | --- | --- | --- |
| `pending` | V0 对象尚未完成几何判断 | 否 | 否 |
| `confirmed_unchanged` | 学生确认当前几何无须修改 | 是 | 是 |
| `modified` | V0 对象的几何已被修改并保存 | 是 | 是 |
| `deleted` | V0 对象被确认应删除并软删除 | 是 | 否，对象仅保留历史与恢复入口 |
| `added` | 学生新增并成功保存的现状对象 | 不进入 V0 分母 | 是 |

状态按几何操作语义更新，不因属性、照片、问题或讨论变化而改变。一个已经确认的对象后来修改几何时变为 `modified`；恢复历史版本会产生新的修改记录，并根据恢复动作后的对象状态更新为 `modified`、`deleted` 或 `added`，不会抹去既有历史。

### 3.3 校核操作

学生处理对象时只有两个主要路径：

1. **确认几何无误：** 获取短时锁并校验对象版本，通过独立 RPC 写入确认状态，不制造虚假的几何编辑记录。
2. **修改几何：** 沿用显式编辑和保存流程，在保存几何批次的同一事务中更新校核状态、几何版本和操作者信息。

新增对象在首次保存成功后直接进入 `added`。删除 V0 对象进入 `deleted`。等高线的编辑和删除继续写入既有历史，但不创建阶段 2 校核状态。

## 4. 学生端工作流程

### 4.1 进入共享现状空间

学生选择正式教学项目和正式村庄，进入“全班共享现状空间”。系统加载：

- 已发布 V0 与当前共享覆盖结果；
- 建筑、道路和水系的校核状态；
- 当前对象锁和编辑者；
- 当前用户可访问的照片、问题、讨论和历史信息。

个人体验空间不显示正式校核进度，个人空间的任何操作也不影响本阶段数据。

### 4.2 地图上的进度入口

地图只提供一个紧凑的主进度入口，例如：

```text
几何校核 126 / 380    聚焦未校核
```

不在顶部提供“已确认无误、已修改、正在编辑、存在问题”等一长串筛选项，避免工具栏过杂。

点击“聚焦未校核”后：

- `pending` 对象保持正常样式或获得轻度强调；
- 已校核对象降低到约 15%～20% 不透明度，但不从地图消失；
- 当前正在编辑的对象显示临时蓝色轮廓和编辑者姓名；
- 存在未解决问题的对象显示红色问题标记；
- 再次点击即可退出聚焦模式。

“确认无误”和“已修改”的区别放在对象详情及管理员统计中。问题浏览继续使用现有问题列表，不混入校核筛选菜单。

### 4.3 单对象处理顺序

1. 学生选择对象，查看当前几何状态和是否有人正在编辑。
2. 如果几何正确，执行“确认几何无误”。
3. 如果几何错误，进入编辑模式，修改、删除或重新新增后显式保存。
4. 几何校核成功后，该对象的属性、照片、问题和讨论入口对全班开放。
5. 后续学生仍可重新修改该对象几何；保存成功后更新校核状态和修订号。

系统不根据某位学生是否亲自完成几何来限制后续操作。只要共享对象已经完成几何校核，其他学生就可以继续补充现状信息。

### 4.4 后续操作门禁

门禁由服务端依据对象校核状态执行，前端禁用仅用于解释和引导：

- `pending`：禁止属性更新、照片上传、创建问题和发表评论；入口显示“请先完成几何校核”。
- `confirmed_unchanged`、`modified`、`added`：允许后续操作。
- `deleted`：禁止新增后续内容，但允许查看历史、既有信息和管理员恢复入口。

客户端不能通过直接调用旧接口绕过门禁。已有 RPC 和写入策略需要统一接入同一校核判断。

## 5. 混合进度口径

### 5.1 固定 V0 主进度

主进度用于回答“原始数据校核了多少”，分母固定为 V0 发布时建筑、道路和水系对象数：

```text
V0 已校核数 = confirmed_unchanged + modified + deleted 的 V0 对象数
V0 校核总数 = V0 中建筑 + 道路 + 水系对象数
```

新增对象不进入固定分母，也不增加主进度分子。这样即使现场持续新增或删除对象，课程进度仍保持可比较。

### 5.2 动态现状规模

当前对象数用于回答“此刻地图上有多少有效现状对象”：

```text
当前有效对象数 = V0 总数 - 已删除 V0 对象数 + 当前有效新增对象数
```

管理员端同时显示新增、删除和当前有效对象数。例如：V0 共 380 个，已校核 126 个，新增 8 个，删除 3 个，则主进度为 `126 / 380`，当前有效对象数为 `385`。

### 5.3 分层统计

管理员可以按建筑、道路和水系查看固定 V0 进度，以及 `confirmed_unchanged`、`modified`、`deleted`、`added` 的数量。学生端默认只显示总进度，避免增加认知负担。

## 6. 并发、锁和实时同步

### 6.1 对象锁

- 开始确认、修改或删除几何前获取短时对象锁。
- 锁以教学项目、村庄、空间、图层和系统对象编码为范围。
- 锁定期间显示编辑者和剩余时间；其他学生不能保存覆盖。
- 编辑过程中按既有心跳机制续期；退出、保存或取消时主动释放。
- 客户端异常退出后等待租约自然到期，不创建永久死锁。

### 6.2 乐观版本校验

每个校核对象维护单调递增的 `geometry_revision`。确认或保存请求必须携带客户端读取时的期望修订号：

- 修订号一致才允许提交；
- 修订号已变化时返回冲突，拒绝状态和几何写入；
- 前端重新加载对象，并清楚提示“对象已被其他同学更新”。

即使短时锁因网络延迟过期，版本校验也必须阻止旧数据覆盖新数据。

### 6.3 实时事件

共享空间订阅以下变化：

- 校核状态和进度变化；
- 几何修订和软删除变化；
- 对象锁的获取、续期和释放；
- 问题状态和必要的对象提示变化。

实时消息只作为界面刷新信号，数据库仍是事实来源。重新连接后必须拉取最新状态，不能仅依赖遗漏的实时事件恢复数据。

## 7. 管理员端“共享现状校核”模块

### 7.1 项目上下文

管理员先选择教学项目、正式村庄和对应的 `formal_shared` 空间。页面必须持续显示当前上下文，禁止对名称相似但属于其他学期或村庄的空间执行统计、恢复或冻结。

### 7.2 校核总览

总览显示：

- 固定 V0 总进度和分层进度；
- 确认无误、已修改、已删除和新增数量；
- 当前有效对象数；
- 已关联照片数；
- 未解决问题数；
- 当前活动编辑者及被锁对象。

### 7.3 对象校核列表

管理员可按图层、几何状态和最近操作者筛选，定位对象并查看：

- 当前几何和 V0 几何；
- 当前属性；
- 照片与问题；
- 最近操作者和更新时间；
- 几何修订号与历史批次。

该列表用于了解进度、发现异常和恢复数据，不提供任务分配功能。

### 7.4 历史与恢复

管理员可查看对象的修改批次和版本，将选定历史状态恢复为共享现状的最新状态。恢复动作必须：

- 经过锁和版本检查；
- 写入新的变更批次与版本记录；
- 保留原有错误记录，不就地篡改历史；
- 不改变任何已经冻结的快照。

## 8. 冻结版本与小组底图

### 8.1 冻结前检查

管理员发起冻结时，系统生成下一版本号，并要求填写或确认版本名称和说明。冻结前检查：

- 教学项目、村庄和共享空间上下文是否一致；
- 是否存在仍有效的对象编辑锁；
- 当前数据和必要关联是否可完整读取；
- 是否已有相同版本号。

如存在活动锁，首版直接阻止冻结并列出对象及编辑者，不提供强制冻结。

### 8.2 原子快照

冻结在一个数据库事务中完成，任何步骤失败都不产生半成品版本。快照包含：

- 建筑、道路、水系以及平台需要的其他当前有效图层的几何和属性；
- 软删除墓碑或等价的删除统计，用于审计和版本比较；
- 冻结时有效的照片关联；
- 冻结时当前问题的关联及其对应修订；
- 版本统计摘要、来源空间和创建者。

照片二进制文件不复制，但其存储对象必须不可变，并在仍被快照引用时禁止物理删除。问题内容使用冻结时的修订引用，后续编辑不能改变旧快照看到的内容。对象讨论和完整操作历史不复制到小组底图；管理员仍可在原共享空间审计历史。

### 8.3 冻结后的行为

- 快照一经完成不可修改。
- 共享现状空间继续可编辑，并可在以后冻结 V2、V3。
- 管理员可把某个冻结版本标记为“推荐小组底图”。
- 新建小组空间时显式记录所用快照 ID。
- 新快照不会自动更新既有小组空间；升级或重建必须由管理员确认。
- 小组空间中的现状几何、属性、照片和问题证据只读；方案要素和小组讨论在阶段 3 独立产生。

## 9. 数据模型设计

### 9.1 新增 `survey_feature_reviews`

该表只保存校核主状态，不重复照片、评论和问题统计。

建议字段：

- `id uuid primary key`
- `teaching_project_id uuid not null`
- `village_id uuid not null`
- `space_id text not null`
- `layer_key text not null`
- `object_code text not null`
- `is_v0_baseline boolean not null`
- `baseline_object_code text`
- `geometry_status text not null`
- `geometry_revision bigint not null default 0`
- `first_reviewed_by uuid`
- `first_reviewed_at timestamptz`
- `latest_modified_by uuid`
- `latest_modified_at timestamptz`
- `latest_geometry_batch_id uuid`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

唯一约束：

```text
(teaching_project_id, village_id, space_id, layer_key, object_code)
```

约束保证 `geometry_status` 只取受控值；V0 对象必须有基线编码，新增对象不得伪装为 V0。服务端从认证用户和空间上下文写入操作者，不接受客户端提交任意用户身份。

### 9.2 复用既有表

- `feature_edit_locks`：扩展或确认完整项目、村庄和空间上下文。
- `feature_change_batches`、`feature_versions`：保存几何编辑、删除和恢复历史。
- `feature_snapshots`、`feature_snapshot_items`：保存不可变冻结版本及对象内容。
- `object_photos`：继续保存照片及对象关联。
- `community_tasks` 或现有问题表：继续保存问题及处理状态。
- `object_comments`：继续保存对象讨论，但不进入小组底图。
- `activity_events`：记录确认、编辑、删除、恢复和冻结等行为。

照片数、问题数和讨论数在需要时按上下文和对象编码聚合，不写入 `survey_feature_reviews`，避免计数漂移。

### 9.3 快照关联扩展

为冻结版本增加受控关联结构，记录快照所引用的照片 ID、问题 ID 和问题修订 ID。可以采用独立关联表，也可以在现有快照明细中使用规范化 JSONB；实施时优先选择可建立外键、索引和 RLS 的独立关联表。

`feature_snapshots` 增加或规范：

- 教学项目、村庄和来源共享空间；
- 单调递增版本号；
- 推荐底图标识；
- 冻结统计摘要；
- 不可变状态和创建者。

## 10. RPC、事务与权限

### 10.1 核心 RPC

1. `confirm_survey_feature_geometry`：校验成员身份、共享空间类型、图层范围、锁令牌和预期修订号，写入确认状态并记录活动。
2. `save_feature_edit_batch`：在既有批量保存流程中加入校核状态、软删除、系统对象编码和修订号更新，所有变化同一事务提交。
3. `restore_survey_feature_version`：仅管理员或教师可调用，以新批次恢复对象。
4. `freeze_shared_survey_snapshot`：仅管理员或教师可调用，检查活动锁并原子生成快照及关联。
5. 只读统计 RPC：按当前上下文返回学生进度摘要和管理员分层统计，避免前端跨表自行拼接并泄漏数据。

为兼容旧调用保留的 RPC 包装器必须解析到唯一项目上下文；无法唯一解析时拒绝请求，不能回退到任意默认村庄。

### 10.2 RLS 与授权

- 当前教学项目成员可读取其有权进入的共享空间校核状态。
- 学生不能直接写 `survey_feature_reviews`，只能调用经过校验的 RPC。
- 学生可在正式共享空间对允许图层执行确认和几何保存。
- 管理员和教师可查看完整统计、历史并执行恢复与冻结。
- 匿名用户无权读取或写入校核、锁、历史和快照数据。
- 跨项目、跨村庄、跨空间访问必须被 RLS 和 RPC 双重拒绝。
- `security definer` RPC 固定安全的 `search_path`，撤销 `public` 和 `anon` 执行权限，并从 `auth.uid()` 推导操作者。

## 11. 错误处理

- **锁冲突：** 返回当前编辑者和租约到期时间，不覆盖保存。
- **版本冲突：** 确认或保存整体拒绝，前端刷新对象；不得单独推进校核状态。
- **保存失败：** 几何、历史批次、校核状态和活动记录整体回滚。
- **照片上传失败：** 清理未完成上传，不建立错误关联，也不改变校核状态。
- **实时断线：** 明确显示离线或不同步状态，暂停共享写入，不把本地操作显示为已保存。
- **冻结冲突：** 存在活动锁时阻止冻结并列出详情。
- **冻结失败：** 对象、关联和版本元数据整体回滚。
- **恢复失败：** 当前共享数据保持不变。
- **无效上下文：** 项目、村庄和空间任一不匹配时拒绝操作，不自动猜测默认空间。

## 12. 测试与验收

### 12.1 数据库契约

- 迁移可重复执行，不重复生成状态、索引、触发器、策略或 V0 初始化记录。
- V0 建筑、道路和水系正确初始化为 `pending`，新增对象不会进入 V0 分母。
- 校核状态约束、唯一约束、软删除和修订号单调递增有效。
- 所有写入 RPC 从登录身份确定操作者，并拒绝匿名、跨项目和跨村庄调用。
- 旧接口不能绕过几何门禁写入属性、照片、问题或讨论。

### 12.2 核心协作场景

1. 学生甲确认某对象几何无误后，主进度增加，学生乙立即看到完成状态，并可处理该对象后续信息。
2. 学生甲编辑对象时，学生乙看到锁和编辑者，不能覆盖保存。
3. 学生甲打开旧版本后学生乙先保存，甲的确认或保存被拒绝并刷新。
4. `pending` 对象的属性、照片、问题和讨论写入均被前端和服务端阻止；校核完成后开放。
5. 修改、删除和新增对象后，固定 V0 进度、分类数量和动态当前对象数符合混合口径。
6. 照片、属性、问题和讨论变化不错误改变几何校核进度。
7. 实时重连后，进度、当前编辑者和对象状态与数据库一致。

### 12.3 冻结与恢复场景

1. 存在活动锁时冻结被阻止；锁释放后可以成功冻结。
2. 冻结 V1 后，共享现状仍可编辑，V1 内容保持不变。
3. V1 的几何、属性、照片关联和问题修订不受后续共享空间修改影响。
4. V1 不包含对象讨论，但原共享空间仍保留完整讨论和操作历史。
5. 冻结 V2 后，使用 V1 的既有小组空间不会自动变化。
6. 恢复历史对象会形成新记录，不修改 V1、V2 或旧历史。

### 12.4 界面与回归

- 学生端只显示紧凑主进度和“聚焦未校核”，不会恢复冗长状态下拉列表。
- 聚焦模式只弱化已校核对象，不隐藏它们；锁和问题提示仍可识别。
- 对象门禁提示清楚说明需要先完成几何校核。
- 管理员总览、列表、历史和冻结流程在常规及较窄桌面宽度下可用。
- 米埗村个人体验空间、练习共享空间、正式个人空间及现有二维/三维功能不退化。
- SQL 静态契约测试、本地前端测试和真实 Supabase RPC/RLS 验证全部通过。

## 13. 非目标

- 在线布置、分配、领取或认领校核任务。
- 教师逐条审批学生修改。
- 将属性、照片、问题或讨论分别做成主进度分母。
- 等高线、耕地和开放空间的逐要素校核进度。
- 冻结后把共享现状空间锁为只读。
- 自动把新冻结版本推送到已有小组空间。
- 小组方案编辑、最终成果提交、排版、评分和方案评审。
- 把对象讨论复制到小组方案空间。

## 14. 推荐实施边界

阶段 2 可以作为一个完整实施计划，但应按以下顺序分批验证：

1. 数据库校核状态、不可变对象编码、修订号、RPC、RLS 与 V0 初始化。
2. 学生端对象校核动作、门禁和混合进度。
3. 对象锁、版本冲突和实时同步。
4. 管理员总览、对象列表、历史恢复与冻结前检查。
5. 冻结快照关联、小组底图来源记录和跨版本验证。
6. 真实 Supabase 环境部署、端到端协作测试和响应式界面验收。

阶段 3 只依赖阶段 2 输出的不可变快照 ID，不依赖共享空间停更，也不依赖教师逐条批准历史修改。
