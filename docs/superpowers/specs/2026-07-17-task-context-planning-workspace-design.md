# 村庄规划平台“任务—情境工作区”总体设计

> **过程文档｜总体设计说明**
>
> 本文记录 2026-07-17 讨论确认的平台重组方案，用于解释后续改造的教学逻辑、界面结构和数据边界。它不是平台运行文件，也不表示文中功能已经完成。
>
> 本文是当前总体设计依据。与早期“独立课程任务页”“七阶段任务栏”或“课程栏叠加原菜单栏”等设计发生冲突时，以本文为准。

## 1. 背景与问题

平台已经具备 2D、3D、照片上传、评论、要素编辑、规划空间和后台行为记录等能力，但功能入口按照技术模块堆叠，学生需要自己理解“共建模式、规划模式、图层、空间工具、2D、3D”等概念，教学任务与地图操作之间缺少稳定联系。

本次改造不再新增一套独立课程页面，而是在原有地图平台上建立“任务决定情境，情境组织工具和信息”的统一工作区。学生始终停留在同一个地图界面中，课程阶段只改变默认关注内容，不强制关闭其他功能。

## 2. 设计目标

- 让学生从调研、校核、诊断、方案设计到成果提交始终使用同一工作区。
- 用教学阶段组织资料与操作，取消抽象的“共建模式／规划模式”总开关。
- 让 2D 与 3D 成为同一数据的两种视图，而不是两个相互跳转的平台。
- 支持全班共同校核现状、小组私有编辑方案以及教师统一管理和课堂展示。
- 保留每次数据修改和学生行为记录，服务教学回溯与后续论文研究。
- 在不牺牲现有能力的前提下减少重复入口、空白侧栏和信息割裂。

## 3. 本轮不处理的内容

本轮总体设计不确定按钮文字、图标样式、具体表单字段、像素尺寸和最终视觉主题，也不要求一次性重写全部后台结构。上述内容应在各实施阶段结合现有代码和数据表单独确认。

## 4. 总体信息架构

工作区由六个稳定区域组成。

### 4.1 最左侧课程阶段栏

最左侧使用可收缩的窄图标栏，展示两个准备状态和四个实践阶段。它负责课程导航和进度提示，不承载地图图层或编辑工具。

课程采用柔性引导：学生可以查看和进入任意阶段，不会因为上一步未完成而看不到后续内容。阶段状态只用于提醒、统计和教师了解进度。

### 4.2 阶段情境侧栏

课程阶段栏右侧是当前阶段的情境侧栏，并直接替代原来的“菜单”列。它优先显示：

1. 本阶段需要形成的成果；
2. 与本阶段最相关的资料；
3. 建议使用的主要操作。

情境侧栏不重复列出全部图层、版本、空间管理和导出功能。学生切换阶段时只改变默认关注点，不会丢失地图状态，也不会被禁止使用其他已开放能力。

### 4.3 地图顶部上下文栏

当前村庄、班级／小组空间、当前数据版本以及 2D／3D 切换放在地图顶部的稳定上下文栏中。它们属于整个工作空间，而不是某个课程阶段。

### 4.4 中央地图工作区

中央区域始终用于展示和操作地图。切换阶段、展开侧栏或切换 2D／3D 时不离开当前工作区，也不重新进入另一个平台页面。

### 4.5 右侧对象信息与协作面板

右侧栏统一服务于当前选中的地图对象。未选中对象时仅显示简洁操作提示；选中建筑、道路、照片、问题点或方案对象后，显示与对象有关的信息。

面板在不同阶段保持相同心智模型，主要内容包括：

- 属性；
- 照片与资料；
- 讨论；
- 修改历史。

现状校核时突出校核状态、调研证据和班级讨论；方案设计时突出方案参数、小组说明和版本变化。学生不在此处看到占据大量空间的个人操作流水，教师后台仍可查询完整行为记录。

### 4.6 图层与项目设置抽屉

全部图层、底图、空间管理、基线同步、版本、导出等低频但重要的全局能力，集中到“图层与项目设置”抽屉。它们不跟随课程阶段反复出现，也不挤占情境侧栏。

## 5. 教学流程

### 5.1 两个准备状态

- **加入小组**：学生使用自己的账号加入线下预先形成的小组；教师可预建小组，学生也可按允许的方式加入。
- **学习准备**：提示学生完成首页的教学目的、理论学习和村庄信息阅读。

这两项是准备状态，而不是两个完整地图作业阶段。

### 5.2 四个实践阶段

1. **调研采集与现状校核**：全班共同修正教师提供的初始现状要素，补充缺失对象、属性、现场照片和调研说明。
2. **现状诊断与课堂汇报**：全班共享问题标记、要素讨论、问题清单、汇报结论和教师反馈。小组线下讨论与课堂交流是主要协作形式，不单设“协作评审”阶段。
3. **方案设计与迭代**：各小组从教师冻结的现状校核基线生成私有规划空间，在同一份方案数据上切换 2D 与 3D 进行编辑和检查。
4. **成果整理与提交**：小组确认冻结版本、方案说明和附件，保留个人反思与小组成果，并提交给教师。

## 6. 现状校核与方案数据流

### 6.1 初始现状版本

教师提供精度不高但结构完整的初始现状矢量版本 `V0`。该版本只读并永久保留，用于比较和恢复，不允许学生直接覆盖。

### 6.2 全班共享校核层

所有学生共同编辑一份现状校核工作层，可以：

- 修改建筑、道路等现状轮廓和属性；
- 补充遗漏对象；
- 再次修改其他同学已经校核过的对象；
- 上传并关联现场照片、调研说明和问题讨论。

共享编辑不是最后写入者无痕覆盖。每次修改都形成版本记录，保留作者、时间、对象、修改前后内容和必要的恢复依据。

### 6.3 教师冻结校核基线

调研与课堂汇报后，教师从共享校核层冻结现状基线 `V1.0`。冻结版本作为各小组方案设计的共同起点，确保不同小组使用相同现状基础。

冻结后，全班共享校核层仍可继续修正。若教师发布新的 `V1.1`，已经建立的小组方案不会被静默覆盖；每个小组明确选择是否同步，并在同步前看到可能影响的对象。

### 6.4 小组私有方案空间

每个小组从同一冻结基线生成独立方案空间。组内成员共享编辑，其他学生默认不可浏览；教师和管理员可以查看全部小组，并可在课堂或成果展示时选择性发布某组版本。

## 7. 2D 与 3D 的关系

2D 与 3D 是同一工作区、同一数据和同一选中对象的两种视图。切换视图时保持当前村庄、小组空间、课程阶段、图层状态和对象上下文。

- 2D 负责轮廓、位置、属性和大部分规划要素编辑。
- 3D 负责方案展示、空间检查和三维表达。
- 3D 可补充白模替换、建筑高度／层数以及必要的旋转、缩放等能力，但不另建一套课程阶段工具体系。
- 漫游、视角、测量等三维基础控制放在场景边缘，不占用阶段情境侧栏。

因此，3D 中的左侧不再是空白或禁用提示，而是继续显示与 2D 相同的当前阶段成果、资料和主要操作。

## 8. 问题与讨论

讨论使用两种空间关联方式，但进入同一套评论与回复体系：

1. 新增点状问题标记，并围绕该位置发表说明、照片和回复；
2. 直接选择建筑、道路等现有矢量要素，在对象的“讨论”中留言。

问题标记首期只使用点，不扩展线和面绘制。问题点与要素评论均保留作者、时间、回复关系及关联资料。同一位置或同一对象可以存在多条判断和证据，讨论以追加方式共存，不互相覆盖。

## 9. 可见性与权限

- 初始现状 `V0`：全班可见、只读。
- 现状校核工作层：全班可见、可按课程权限编辑、完整留痕。
- 调研照片、调研记录、问题点、诊断结论、课堂汇报结论和教师反馈：全班共享。
- 小组方案草稿及其讨论：仅本组成员和教师／管理员可见。
- 已提交或课堂展示的成果：由教师决定何时向其他学生开放。
- 管理员和教师拥有小组管理、基线冻结、版本发布、全班查看和成果展示权限；普通学生仅拥有课程范围内的编辑和协作权限。

## 10. 日志与版本记录

平台保留两套彼此独立的记录：

- **学生行为日志**：后台记录登录、阶段访问、要素增删改、照片上传、评论、版本操作、同步和提交等事件，用于教学管理与论文分析。学生端不展示连续的原始事件流水。
- **平台迭代日志**：`docs/PLATFORM_ITERATION_LOG.md` 记录项目代码和功能每次迭代的大致内容，属于开发过程文档，不等同于学生行为数据。

现状要素和方案要素的版本历史属于业务数据，应能回答“谁在何时修改了什么”，并支持教师追溯和必要的版本恢复。

## 11. 异常与冲突处理原则

- 未加入小组时可以浏览所有课程阶段和公共现状资料，但涉及小组私有方案的保存操作应提示先加入小组，而不是隐藏整个阶段。
- 网络或数据库保存失败时不得显示为成功；界面应保留未提交内容并允许重试。
- 多人先后修改同一现状对象时保留完整版本链，不做无痕覆盖；发生并发冲突时提示用户基于最新版本确认修改。
- 基线升级不得自动改写小组方案；同步必须由小组明确触发，并记录同步来源和结果。
- 3D 加载失败时不影响 2D 数据编辑；用户可返回 2D，且当前空间和任务上下文不丢失。

## 12. 验收原则

- 学生进入互动平台后直接看到统一地图工作区，不再经过独立课程任务页或 2D／3D 入口卡片。
- 阶段栏可收缩，切换阶段不会离开地图或重建工作空间。
- 后续阶段始终可查看，未完成前序阶段只产生柔性提醒。
- 原“菜单”列被阶段情境侧栏替代，不同时保留两套侧栏。
- 右侧栏围绕当前对象组织属性、资料、讨论和历史。
- 2D／3D 切换后仍处于同一村庄、同一数据空间和同一课程阶段。
- 全班可共同校核现状且每次修改可追溯；`V0` 不被覆盖。
- 各小组从同一冻结基线建立互相不可见的私有方案空间。
- 问题点留言和现有矢量要素留言均可正常关联、回复和追溯。
- 教师可查看全部小组、冻结／发布基线并控制成果展示。
- 后台行为记录持续工作，但学生界面不再出现原始“最近操作”列表。

## 13. 建议实施边界

该总体改造应拆分为可独立验证的实施阶段，避免一次性重写整个平台：

1. 重组统一工作区外壳、课程阶段栏、情境侧栏、顶部上下文栏和右侧对象面板；
2. 整合全班现状校核、照片／问题关联和对象版本历史；
3. 建立冻结基线、小组私有方案空间及显式基线同步；
4. 完善成果提交、教师管理和研究所需的行为查询／导出。

每个阶段应复用现有 2D、3D、照片、评论、要素编辑和 Supabase 能力，先核对既有数据表与接口，再决定最小数据库变更。本文不授权删除现有功能或未经确认地迁移生产数据。

## 14. 2026-07-20 界面与原功能恢复补充设计

本轮采用“在任务—情境工作区中恢复原能力”的方案 A，不退回旧版功能堆叠菜单。

- 课程阶段轨道保持 68px 常驻；展开后相邻情境栏保持约 290px，二者顶部高度、图标尺度和折叠状态一致，不再出现重复或尺寸突兀的首页入口。
- 地图顶部栏保持单行紧凑布局，并随左侧情境栏、右侧对象栏的展开状态改变边界。
- 右侧对象栏的折叠按钮必须停靠在对象栏实际边缘；对象栏收起后按钮贴近窗口右侧，顶部栏同步扩展。
- 空间选择器右侧常驻“新增、重命名、删除”三个空间管理按钮；设置抽屉不再重复展示这三个按钮。系统现状空间不可删除，管理员可管理全部非系统空间，普通学生只能重命名或删除自己创建的空间。
- 顶部提供清晰的“标记问题”和“班级讨论”入口。标记问题填写说明后只需在地图点击一个点；班级讨论继续显示作者、时间、照片、点赞、回复与定位。
- 选择建筑、道路等矢量对象后，右栏按“属性、照片、讨论、修改历史”的顺序组织。建筑照片在现状与规划空间中使用同一照片命名空间，不因当前空间不同而隐藏上传入口。
- 对象讨论复用现有 `object_comments` 表；点赞和回复复用 `object_attribute_edits` 的 JSON 交互记录，不新增数据库迁移。
- 本轮只恢复入口、前端接线和现有权限逻辑，不执行 Supabase SQL，不创建 Git 提交。
