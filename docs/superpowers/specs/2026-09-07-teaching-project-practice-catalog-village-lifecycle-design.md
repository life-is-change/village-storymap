# 教学项目、全局练习村目录与村庄生命周期设计

## 目标

解决已发布练习村无法出现在首页和工作区的问题，并建立可跨学期复用的教学项目机制以及安全、可恢复的村庄删除/归档流程。

本次设计遵循三个已经确认的业务规则：

1. 教学项目代表某一学期的一次课程运行。
2. 所有已发布且未归档的练习村默认对所有当前教学项目开放。
3. 未投入使用的村庄可永久删除；已投入使用的村庄只能归档。

## 已确认的根因

现有 `teaching_projects.practice_village_id` 只保存一个练习村。`get_active_project_context`、前端 `getActiveContext`、工作区条目构造和首页数据构造又都只保留这个练习村与当前正式村。因此，红星村即使已经成功发布 V0，只要没有成为 `practice_village_id`，就会被上下文层过滤。

此外，`teaching_projects.course_id` 当前具有唯一约束，同一课程模板无法自然创建下一学期项目；后台也缺少结束当前项目和创建下一项目的完整入口。

## 领域模型

### 课程与教学项目

- `courses` 是可复用的课程模板，例如“村庄规划课程”。
- `teaching_projects` 是某一学期的课程实例，例如“2027 春季村庄规划课程”。
- 同一个 `course_id` 可以有多个历史教学项目。
- 系统仍只允许一个 `stage not in ('completed', 'archived')` 的当前教学项目，避免学生误入其他学期。
- 教学项目名称继续承担学期标识，不新增重复的学期字段。
- 新教学项目初期可以没有正式村庄；数据准备完成后再绑定一个已发布的非练习村。
- 一个教学项目最多绑定一个正式村庄；同一正式村庄可以在不同学期再次使用，但课程空间和成果按教学项目隔离。

### 练习村

- `practice_village_id` 暂时保留，语义调整为“默认练习村”，用于兼容米埗村、理论学习入口和旧数据。
- 可访问练习村集合不再来自单个字段，而是全部 `is_practice = true and status = 'published'` 的村庄。
- 当前项目的可选村庄为“全部已发布练习村 + 已开放的当前正式村庄”。
- 首页采用相同集合，避免首页与工作区出现不同结果。
- 默认进入顺序为：用户上次选择、默认练习村、其余练习村、正式村庄。
- 练习村 V0 数据全局复用；共享空间和个人空间仍绑定 `teaching_project_id + village_id`，不同学期互不混合。

## 数据库迁移

新增一份命名迁移：

`supabase_SQL/Teaching Project Practice Catalog and Village Lifecycle.sql`

迁移必须可重复执行并处于单个事务中，包含：

1. 删除 `teaching_projects.course_id` 的唯一约束，改建普通索引。
2. 保留“全库最多一个当前教学项目”的部分唯一索引。
3. 更新 `get_active_project_context()`，返回所有已发布练习村以及当前项目已开放的正式村；管理员仍通过独立村庄列表查看草稿和归档项。
4. 新增 `ensure_all_project_practice_spaces(project_id)`，为一个项目的全部已发布练习村建立唯一的 `practice_shared` 空间。
5. 创建教学项目时调用上述函数；新的练习村发布时，为当前项目补建共享空间；迁移执行时为当前项目回填已有练习村空间。
6. 更新项目上下文校验，使当前项目中的任意已发布练习村都可以建立 `practice_personal` 空间；正式村仍必须等于项目的 `formal_village_id`。
7. 新增教学项目归档、村庄删除预检、村庄归档、恢复和未使用村庄永久删除 RPC。
8. 所有新 RPC 使用 `security definer`、固定 `search_path`、管理员角色校验，并撤销 `public`/`anon` 默认执行权限。

## 教学项目生命周期

后台“村庄与项目”页面增加独立的“教学项目”区：

- 当前项目卡片显示名称、课程模板、阶段、默认练习村和正式村庄。
- “结束并归档当前项目”需要二次确认，将阶段设为 `archived`，不删除任何课程成果。
- 当前项目归档后，可创建下一学期项目；表单填写项目名称、选择课程模板和默认练习村。
- 创建成功后，系统为所有已发布练习村生成该项目的共享练习空间。
- 正式村庄仍在其 V0 发布后通过现有“绑定为本学期正式村庄”操作加入项目。

RPC：

- `archive_teaching_project(p_project_id uuid)`：仅管理员可执行；幂等地把非归档项目设为 `archived`。
- 现有 `create_teaching_project(...)`：移除同课程不可重复的数据库限制，保留同一时间只能有一个当前项目的限制，并补建全部练习空间。

## 村庄使用判定

“已投入使用”指村庄已产生任一项目引用或用户成果，包括：

- 是任一教学项目的默认练习村或正式村；
- 存在 `planning_spaces`；
- 存在要素、编辑批次、编辑锁、快照或校核记录；
- 存在照片、属性编辑、讨论、问题、活动记录；
- 存在小组基线更新、冲突或版本记录；
- 存在个人图底、地理处理任务等其他以该村庄为上下文的业务数据。

V0 数据集和村庄实景模型配置本身不算学生投入使用，因为它们属于永久删除时应随村庄一起清理的管理员准备数据。数据库外键仍作为最终防线：任何预检遗漏都必须让永久删除失败，而不是级联误删学生成果。

## 删除、归档与恢复

### 删除预检

`get_village_removal_preview(p_village_id uuid)` 返回：

- 村庄基本状态；
- 是否为受保护的米埗村；
- 是否被当前或历史项目引用；
- 各类课程/用户数据计数；
- V0 数据集、实景模型和 Storage 文件路径；
- 允许动作：`delete`、`archive` 或 `blocked`；
- 阻止原因码。

### 永久删除

仅在预检结果为 `delete` 时开放：

1. 管理员确认村庄名称和删除摘要。
2. 前端通过 Supabase Storage API 删除预检返回的 `village-datasets` 精确路径；不得使用模糊前缀删除其他村庄文件。
3. Storage 删除全部成功后调用 `delete_unused_village(p_village_id uuid)`。
4. RPC 在事务内重新执行使用判定，防止预检后产生新数据；若条件变化则拒绝删除。
5. RPC 删除数据集、实景模型和村庄记录。数据库外键异常统一映射为 `VILLAGE_IN_USE`。
6. Storage 删除失败时不删除数据库记录，并保留可重试状态。

### 归档与恢复

- `archive_village(p_village_id uuid)` 将村庄设为 `archived`，不删除 V0、空间或学生成果。
- 当前项目绑定的正式村庄不允许直接归档，返回 `ACTIVE_FORMAL_VILLAGE_REQUIRED`；管理员需先结束项目。
- 米埗村不允许归档或永久删除，返回 `SYSTEM_VILLAGE_PROTECTED`。
- 已归档练习村不再出现在首页、新项目和普通工作区选择器中。
- `restore_village(p_village_id uuid)` 根据已发布/ready 数据集恢复为 `published`、`data_ready` 或 `draft`；历史成果保持原样。

## 前端数据流

### 村庄上下文

- `features/villages/village-client.js` 不再用 `practiceVillageId/formalVillageId` 二次过滤 RPC 返回的村庄。
- `features/villages/village-model.js` 从所有已发布练习村构建项目条目和首页条目，并只追加当前项目开放的正式村。
- 首页 iframe 继续使用 `village-home-context` 消息，不新增第二套数据来源。
- 工作区切换目标时继续执行项目、村庄和空间三层校验。

### 管理后台

- 村庄列表展示类型、发布状态、使用状态和可执行动作。
- “永久删除”“归档”“恢复”均先读取服务端预检，不以浏览器本地计数决定权限。
- 危险操作使用现有自定义确认框；永久删除文案明确列出数据集、实景配置和 Storage 文件数量。
- 教学项目区负责归档本学期和创建下一学期，不把课程生命周期混入村庄创建三步流程。

## 错误处理与安全

- `ACTIVE_PROJECT_ALREADY_EXISTS`：存在未归档项目时禁止创建下一项目。
- `PUBLISHED_PRACTICE_VILLAGE_REQUIRED`：默认练习村必须已发布。
- `SYSTEM_VILLAGE_PROTECTED`：米埗村禁止删除或归档。
- `ACTIVE_FORMAL_VILLAGE_REQUIRED`：当前正式村必须先结束项目。
- `VILLAGE_IN_USE`：永久删除前发现项目引用或用户成果。
- `VILLAGE_NOT_FOUND`：目标不存在。
- `STORAGE_CLEANUP_FAILED`：Storage 清理失败，数据库保持不变。
- 所有写入 RPC 只授予 `authenticated`，并在函数内部要求管理员角色。

## 测试策略

遵循测试驱动开发，先观察回归测试失败，再实施：

1. 模型测试：多个已发布练习村同时进入工作区和首页；草稿、归档练习村不可见。
2. 客户端契约测试：不再进行单练习村二次过滤，并调用新增项目/生命周期 RPC。
3. 管理员控制器测试：动作状态、预检、二次确认、Storage 清理失败不删除数据库、归档与恢复。
4. SQL 契约测试：同课程多项目、单当前项目、全局练习目录、管理员权限、删除重检及米埗保护。
5. 集成测试：旧米埗上下文兼容；红星村发布后出现在首页和工作区；新学期进入同一练习村时空间隔离。
6. 全量运行现有 Node 测试，并执行 JavaScript 语法和 `git diff --check` 检查。

## 发布顺序与兼容

1. 先部署数据库迁移，使新旧前端都能读取兼容字段。
2. 再发布前端模型、客户端和管理员 UI。
3. 强制刷新首页与工作区，验证米埗村和红星村同时出现。
4. 使用一个无业务数据的临时村验证永久删除；使用一个已有空间的村验证只能归档。
5. 数据库迁移不修改米埗村 V0，不删除任何现有课程数据。
