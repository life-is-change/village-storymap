# 阿里云业务数据库与 Supabase 4090 通道拆分设计

状态：用户于 2026-10-15 确认设计；阶段 A 实施计划待审阅，尚未实施业务切换。首个交付计划见 [业务 API 内部验证实施计划](../plans/2026-10-15-business-api-validation.md)。

## 用户目标与现状

日常教学、调查、规划和三维设计的数据读写逐步迁至广州阿里云，减少这些操作访问东京数据库的网络往返；4090 的任务提交、处理状态和结果通道先保留在 Supabase。原 Supabase 保留，代码沿用原项目 main → GitHub → 阿里云的更新流程。

阿里云为 2 vCPU / 标称 2 GiB，系统实际报告约 1.6 GiB 内存；当前静态 Nginx 网站已运行。前端仍直接使用 Supabase，所以网站已迁移不等于数据库已迁移。

Windows 已成功导出并离线解码校验数据库归档，随后由用户私有上传阿里云并完成隔离恢复及重启复核。已核对 106 张含数据的表和 14 个序列状态，其中含 4 个 Auth 用户、137 条 Storage 对象元数据。完整归档包含认证资料等私有数据，保留在仓库和网站目录之外。Storage 文件本体尚未复制，数据库备份仅包含其元数据。

## 为什么不能按表名前缀直接拆开

已核对的源代码与归档结构揭示以下依赖：

- 地理处理提交 RPC 检查登录用户、课程成员和教学项目；任务表关联用户、教学项目、村庄和数据集。
- 立面任务关联 `object_photos`，提交 RPC 还检查当前规划空间是否可访问。
- `personal_result_bundles`、`personal_layer_versions` 引用任务 ID；任务结果导入会在同一业务事务内修改个人图层。
- `course_personal_spaces` 引用 `geoprocessing_villages`。该村庄目录同时是业务数据与任务运行配置。
- 调查协作还通过 Realtime 订阅 `survey_feature_reviews` 和 `feature_edit_locks`。Realtime 并不全是 4090 专用。

证据入口：`features/geoprocessing/geoprocessing-client.js`、`features/survey/survey-realtime-controller.js`、`supabase_SQL/Geoprocessing Local Source Inputs.sql`、`supabase_SQL/Facade Generation Worker Queue.sql`。已检查归档中的外键定义，私有归档及其 SQL 不提交 Git。

## 推荐架构与备选路径

选择轻量混合架构：阿里云 PostgreSQL + 业务 HTTP API，暂时保留托管 Supabase Auth 和 GPU 通道。保持同一用户 UUID，避免首期同时迁移身份系统与任务调度。

另两条路径暂不采用：只恢复 PostgreSQL 而保持前端原接口，只能获得副本，无法减少线上业务网络请求；在 2 GiB 上部署完整 Supabase 服务集合会增加内存和维护负担，需另行压测后决定。

| 内容 | 计划主位置 | 迁移要求 |
| --- | --- | --- |
| Nginx 静态网站 | 阿里云 | 沿用当前 Docker 部署 |
| 调查、评论、规划要素、方案和三维设计 | 阿里云 PostgreSQL | 含课程/空间权限、版本、锁与审计；按完整业务模块切换 |
| 登录、刷新会话、身份 UUID | Supabase Auth，首期保留 | 阿里云 API 验证现有访问令牌，不能信任前端传来的用户 ID |
| 地理处理与立面任务、租约、心跳、状态、产物记录 | Supabase | 4090 端点与 Worker 配置首期保持现状 |
| GPU 输入、私有产物与签名 URL | Supabase Storage，首期保留 | 新业务照片作为任务输入时须有受控的上传或引用桥接 |
| 普通业务照片、GLB 等对象文件 | 阿里云持久化存储，后续按模块搬迁 | 单独复制文件、校验哈希与访问权限，再改 URL；保留旧对象 |
| 课程、教学项目、村庄、照片等任务依赖 | 过渡阶段保留 Supabase 必需副本 | 阿里云作为相应业务切换后的主库，建立明确同步/校验机制后才能停止旧业务写入 |

## API 与身份边界

浏览器通过同源 `/api` 访问阿里云业务 API，PostgreSQL 只在 Docker 私有网络内开放。数据库密码和 Supabase service role 不进入静态前端。原来的 `.from()`、`.rpc()` 和 Storage 请求需要逐模块适配，不能只替换 Supabase URL。

API 验证令牌签名、签发者、受众、时效和当前业务权限。先确认项目实际签名算法与密钥配置，再选用受支持的验证方式；没有核实前不假定一定使用非对称 JWKS。数据库使用最小权限角色，在每个事务内设置经验证的身份上下文，复用 RLS 或明确重写等价权限校验，不能用超级用户直接承接全部浏览器请求。

迁移包含 `profiles` 等业务资料，并不意味着删除 Supabase Auth 用户。认证资料与业务资料必须保持相同 UUID；用户停用和权限撤销要有测试。

## 任务依赖与跨库一致性

第一阶段复制并验证完整快照，Supabase 仍是线上主库。此阶段不引入双写，不清理源数据，不会改善线上业务延迟。

业务切换前，为每个模块列出它读取/写入的表、RPC、Storage 路径、Realtime 订阅及权限函数，作为切换清单。不能仅依据命名前缀分组。

任务桥接采用以下约束，具体表级操作需在实现计划中展开：

1. 4090 的队列表与状态流保留在 Supabase，现有任务 ID 不变。阿里云迁入的历史队列副本只用于验证/引用，不能启动第二套消费者。
2. 阿里云提交入口验证本地最新权限；建立课程、教学项目、村庄、用户和必要照片上下文的最小镜像。同步采用事务 outbox、幂等重试与可观测的失败状态；删除使用可同步的撤销/墓碑，避免授权永久残留。
3. 不允许将可直接调用的旧 RPC 继续依赖于过期的权限镜像。提交、取消、结果签名与读取权限必须逐个审计；最终可调用入口与授权来源一致后才切换。需要变更 Supabase RPC 授权时另有版本化迁移与回滚，禁止跳过权限校验。
4. 跨数据库不能维持原来的 PostgreSQL 外键与事务。保留原任务 ID，建立阿里云端受限任务引用/结果记录；只有服务端确认任务所属人与上下文后才写入引用。结果导入在阿里云单个事务中完成，用唯一约束防止重复导入。
5. 新照片进入任务链路前，先确认 Worker 能访问输入。不能把仅在阿里云本地磁盘的路径直接交给现有 Worker。GPU 所需输入继续使用已验证的 Storage 通道，或另行实现受控传输。
6. 调查审核与编辑锁的更新提示必须有本地替代机制。优先评估同源 SSE；若使用定时刷新，需明确可见延迟、锁的原子获取/过期和断线重连，不把通知机制当锁的正确性保证。

## 数据复制、发布与回退

1. 以已校验归档作为恢复验证输入，在独立数据库容器中检查扩展、角色、结构、数据、序列、RLS 与函数。原始 managed 平台内部 SQL 不能覆盖到预置服务而不做兼容处理。
2. 复制普通文件时与业务快照对齐，记录对象清单和校验值。恢复成功与文件可访问分别验收。
3. 首期仅部署业务 API 的内部验证环境，不自动修改线上前端路由。
4. 切换模块时短暂停止该模块写入，完成最终增量/快照与一致性核对，再将该模块读写一起指向阿里云；任务通道保持原端点。切换期间只保留一处业务主写入点。
5. 切换前可直接撤回新路由；切换后若已有阿里云新写入，回退前必须停止写入、导出并回补这些数据或经过验证的反向同步。旧 Supabase 只是切换时点的保留副本，不自动包含新写入。
6. 每次代码与 SQL 改动先在本地 main 测试、提交并推送 GitHub，再在阿里云拉取同一提交部署，记录版本和回退点。

## 资源与验收

预算从 Nginx + 单 PostgreSQL + 小型业务 API 开始，先限制连接池和数据库参数，测量空闲及代表性负载下的内存、CPU、磁盘等待与接口 P50/P95 延迟。不能保证同机部署一定更快，也不能把 Docker 当作减少数据库磁盘 I/O 的手段。

验收必须覆盖：恢复数据一致性；已有用户登录；教师/学生权限隔离；规划与调查保存、版本回退；照片/GLB 访问；编辑锁竞争和重连；4090 提交/取消/产物读取/幂等导入；权限撤销；容器重启后的数据持久性；故障与回退演练。代表性负载下若持续内存压力或交换，先调整服务和查询再决定扩容。

## 副本验证后的交付顺序

这是一项架构迁移，分为以下可独立验收的交付阶段。当前只完成了数据库副本验证；下面的业务服务尚未实现或部署。

### A. 业务 API 内部验证与依赖清单

首个子项目交付轻量业务 HTTP API 的内部验证环境、显式模块路由配置和自动化权限测试。先验证原用户令牌能访问本地业务资料、课程/空间列表，且学生不能访问其他人的私有空间、不能执行教师或管理员操作。无令牌、无效令牌、过期令牌必须拒绝。查询和 RPC 只能调用审定清单中的对象，不能向浏览器提供任意 SQL、任意表/函数执行或超级用户连接。

具体审计入口包括 `app.js` 中的 `supabaseClient` 初始化及空间/场景调用、`features/data/` 的规划和个人版本客户端、`features/survey/` 的审核与通知、`features/models/group-model-library.js`，以及对应的 `supabase_SQL/` 权限和 RPC 定义。每个模块的清单记录表、读写方法、RPC、锁、Storage 桶/路径、通知、权限函数和 GPU 引用；不要把调查 Realtime 误认为 GPU 通道。

新 API 从服务端验证 Supabase 身份，在事务内设置本地 RLS 身份。业务资料来自本地 PostgreSQL；初期验证不修改线上 `supabaseClient` 的全局地址。线上前端保持原路径，只有显式启用的内部测试模块访问新 API。新 API 失败时显示错误，不静默将写入重试到另一数据库，避免两处主写入。

Compose 为 API 和数据库配置私有网络，数据库不发布宿主机端口；Nginx 是唯一公网入口。现有验证副本仍是恢复基线。生产候选采用独立持久化目录/卷，不能用恢复脚本覆盖成功副本；2 GB 机器默认仅运行一个数据库实例，切换验证环境前先保留并停止旧副本。既有数据卷不删除。生产候选的创建、网络调整与停止动作必须在部署脚本中列清并校验目标。

当前网站仅有 HTTP 公网 IP。内部验证可通过 SSH 隧道在本机进行；公网业务 API 正式接入前要配置可用的 HTTPS 入口，避免把现有登录令牌及私有业务请求发往明文 API。HTTPS 的具体入口与证书在部署前核实，不假定用户已有域名。

### B. 文件本体复制与访问服务

先盘点并复制现有对象文件，保留源文件与源路径映射，为每个文件记录桶、对象路径、字节数、SHA-256 和复制状态。普通业务候选包括 `house-photos`、`scene-assets`、`scene-version-previews`、`group-models`、`village-datasets`；须依据实际引用逐项分类，不能把 GPU 所需照片或输入一起从源端删除。`geoprocessing-results` 等任务产物首期保持原有访问通道。

文件保存到仓库和静态网站根目录以外的持久化目录。API 按用户/课程/空间权限授权上传、读取和删除，私有桶不能变成公开目录；保留已有文件大小和类型约束、GLB 低模关联及预览引用。复制只读源，目标路径禁止越界或通过符号链接落入其他目录。先用实际文件逐个校验，不把数据库中的 `storage.objects` 行数当作文件验收结果。

源 Storage 连接需要服务端授权。若后续复制工具确需项目 secret/service-role key，由用户在本机或服务器交互输入，写入私有凭据文件，不进入命令行、日志、Git 或聊天。该密钥不同于数据库密码和 Publishable key。

### C. 普通业务适配、协作及 GPU 桥接

在候选环境中完成调查/照片、规划/个人版本、三维场景/模型库及管理流程的 API 适配；模块连同它的权限、保存、版本和通知一起验收。课程、成员、空间等共享权限依赖不能在两个端点各自修改；先完成本地权威数据及任务最小镜像的同步与撤销检查，再开放会影响 GPU 授权的新写入。

任务提交、取消、状态和结果访问仍走原 Supabase，但用户看到的任务归属、输入照片与本地最新权限必须一致。新照片进入 GPU 输入链路前完成桥接；任务结果导入转为本地事务并保持幂等。协作锁仍由数据库原子获取、续期与释放；本地通知只是传播变化，不能替代锁或冲突检查。

### D. 最新数据交接与正式切换

在业务候选验收通过后，安排明确的模块暂停写入窗口。暂停应覆盖 GitHub Pages 旧页面、阿里云页面和其他客户端的旧写入通道；仅隐藏新页面按钮不能保证源数据静止。GPU 工作流需要读取或修改相同依赖时，也须在交接清单中列出协调方式。

窗口内获取新的只读备份/增量及文件变更清单，在新候选上应用并复核；不能拿已验证的旧快照直接当作当前线上数据。先验证最终数据，再一次性切换模块读写和文件解析入口，记录代码版本、源备份时间、数据主写入点与回退点。阿里云开始接受新写入后，原 Supabase 只保留原时点数据；回退需要回补新增业务数据，不能仅改回 URL。

每个交付阶段的完成条件是：代码在本地 main 测试并提交 GitHub；用户在阿里云执行对应部署命令；云端功能、权限和资源验收结果写入记录。首个交付只开放内部验证，不在尚未完成桥接、文件和最终同步时提前切换线上业务。

## 官方资料核对

- [完整自托管 Supabase 的资源要求](https://supabase.com/docs/guides/self-hosting/docker#system-requirements)：官方当前列出最低 4 GB RAM，推荐 8 GB 以上；本项目的 2 GB 机器因此采用轻量混合方案，仍须实测容量。
- [Supabase JWT 验证](https://supabase.com/docs/guides/auth/jwts)：按项目实际签名配置验证令牌；不把 Publishable key 当作用户令牌或数据库密码。

## 当前执行状态

- 已完成：本机备份与归档校验、私有上传及服务端校验、隔离 PostgreSQL 容器恢复和重启复核、表级依赖初审、迁移边界草案。执行版本为 `63e53c7`，成功标记为 `DB_COPY_RESTORE_VERIFIED_NOT_CUT_OVER`。
- 未完成：业务 API、任务桥接、对象文件复制、应用权限与负载验收及线上切换。网站当前仍访问 Supabase；副本不会自动接收源库后续写入。
- 资源观察：隔离副本验证完成时容器占用 41.98 MiB / 768 MiB，CPU 0.03%；尚不能据此推断教学并发负载或完整服务栈容量。
- 执行方式：阿里云终端由用户手动操作；本地改动先提交 GitHub main，再由用户拉取部署。浏览器工具会话拒绝不通过其他通道绕过。
